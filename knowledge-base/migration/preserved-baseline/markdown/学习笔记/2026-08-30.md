### 我的问题

请解释这段内容中的核心概念、作用、上下文和容易误解的边界。
Recall成功是如何判定的，举例说明

### 选中文本

> Recall@8

### 解释

`Recall@8` 的核心含义是：只看检索结果排名前 8 的候选，检查预先规定的目标是否被召回。在当前实验中，目标是文件；某道题对应的目标文件出现在前 8 名中的任意位置，这道题就判定成功，否则失败。总体 Recall@8 等于成功题数除以总题数。

它在当前上下文中衡量的是第一阶段的文件定位能力，即检索器能否把 Agent 带到正确的源码范围。实验中的“目标文件 Recall@8 为 100%”表示冻结题集的目标文件全部进入了前 8 名。

容易误解的边界是：`@8` 表示前 8 名的截断范围，并非目标必须恰好排第 8；该指标也不要求前 8 个结果全部正确，因此不能替代精确率。它还是文件级指标，不代表已经命中精确函数、完成修改或得到正确答案。当前实验同时出现目标文件 Recall@8 为 100%、精确目标符号召回为 40%，正说明文件召回成功不等于符号召回成功。

例如，某题的目标文件是 `target.py`：它排第 6 时判定成功，排第 9 或没有返回时判定失败。若冻结的 10 道题都在前 8 名中命中各自目标文件，总体 Recall@8 就是 `10 / 10 = 100%`。

## 历史记录迁移 · grep 与 CKB 的职责边界

来源：[[analysis/Code Knowledge Builder 秋招面试官拷问手册|Code Knowledge Builder 秋招面试官拷问手册]] · 原 GUI 记录

执行器：原记录未保存

### 我的问题

这些指标说明 CKB 应该如何与 grep 分工？

### 选中文本

> 文件级 Recall@8、精确符号召回、可见上下文和延迟分别说明什么？

### 解释

#### 核心含义

这段话不是在证明 CKB “比 grep 更强”，而是在划分两种检索能力的职责：CKB 适合从自然语言意图出发，先找可能相关的文件、职责与相邻关系；`git grep` 适合在已经知道源码词汇、符号名或稳定文本片段时，做精确落点。因此，推荐的是“语义定位后再精确核验”的组合流程，而不是二选一。

文中的三组指标也不能互相替代：

- **目标文件 Recall@8**：正确文件是否出现在前 8 个候选中，衡量的是文件级定位，不代表已经找到正确函数或行。
- **精确符号召回**：目标标识符是否被准确找回，体现 `grep` 在已知词形场景中的优势。
- **可见上下文与中位延迟**：分别反映需要交给人或模型阅读的材料量，以及该次实验的响应速度；它们不能单独证明答案正确。

在 Flask 3.1.3 的十题实验里，CKB 与人工 `git grep` 的目标文件 Recall@8 都是 100%，但 CKB 使用的可见上下文更少、该实验中的中位延迟更低，同时精确符号召回只有 40%，明显弱于 `grep` 的 100%。这组结果支持的是“先导航、后落点”，不是“全面替代 grep”。

#### 在当前上下文中的作用

这段内容位于面试拷问手册中，作用是给“为什么不用 grep”一个可守住边界的回答：项目价值主要在自然语言入口、候选压缩和关系导航；当任务进入精确符号核验时，应主动切回符号查询或窄范围 `grep`。这种表述既说明了收益，也保留了失败模式，避免把单次小规模实验包装成普遍结论。

#### 容易误解的边界

1. **“精准词汇”是输入条件，不是 `grep` 理解了语义。** `grep` 匹配的是文本或正则；只有查询词与源码实际词形接近时，它才天然占优。
2. **自然语言命中正确文件，不等于命中正确符号。** 文件级 Recall@8 为 100% 与精确符号召回为 40% 可以同时成立。
3. **24.9 ms 与 73.2 ms 只属于该版本、十题、常驻状态和测量方法。** 不能据此断言所有仓库、冷启动或所有机器上 CKB 都更快。
4. **11,228 与 2,294 tokens 衡量的是可见上下文，不必然等于系统全部计算成本。** 索引构建、常驻内存和预处理应另行报告。
5. **同一榜单若给 `grep` 目标符号、给 CKB 自然语言问题，比较的是两种不同信息条件。** 它能说明各自擅长什么，但不能直接给出工具优劣总排名。

#### 简短测试用例

假设仓库中只有目标实现使用了下面的名字：

```python
# src/auth/session.py
def revoke_refresh_token(token_id):
    ...
```

学习者只知道需求“用户退出后，在哪里让长期登录凭证失效？”。

- CKB 查询：`用户退出后，在哪里让长期登录凭证失效？`
- 精确 `grep` 查询：`git grep -n "revoke_refresh_token"`

前者没有出现 `refresh token`、`revoke` 或函数名，考查的是从意图到候选实现的定位；后者已经拿到了答案中的精确标识符，考查的是从已知词形到行号的落点。若直接比较二者的召回率，输入信息并不对等。反过来，把整句中文直接交给 `grep`，也会刻意让它做不擅长的语义任务，同样不公平。

#### 更公平的对比方案

采用**双轨、配对、盲测**，不要把结果混成一个总分：

1. **意图发现轨**：为每个目标准备不含路径、符号名和源码原词的自然语言问题。CKB 直接接收该问题；`git grep` 工作流接收同一问题，并允许按预先固定的规则，在限定时间内生成至多 5 个关键词或正则查询。查询者不得查看答案或目标文件。这里比较任务成功率、找到目标所需时间、查询次数、打开的候选文件数和阅读 tokens。
2. **精确落点轨**：向两边同时提供同一个真实标识符，例如 `revoke_refresh_token`。这里比较符号或行级召回、误报数以及冷启动和热启动延迟。该轨能诚实检验 `grep` 的核心优势，也能观察 CKB 的精确查询是否退化。
3. **统一实验条件**：冻结同一提交和索引版本；使用同一硬件；冷启动与常驻结果分开；重复多轮并报告中位数和 P95；候选预算统一为最多 8 个文件。由于 `grep` 本身不做相关性排序，若使用 Recall@8，必须提前声明统一的确定性排序规则，否则改报“检查多少个文件后首次命中”。
4. **成对发布结果**：每道题同时公布自然语言输入、允许的 `grep` 查询、目标文件与目标符号；分别报告文件级与符号级指标，并计入索引构建、常驻内存和人工改写查询的成本。

这样可以回答两个不同而实际的问题：不知道源码词汇时，谁更快把人带到正确区域；已经知道精确符号时，谁更可靠地完成落点。预期结论不是单一胜负，而是验证混合工作流是否减少总时间和阅读量，同时不牺牲最终的精确核验。

人工设计 grep 关键词与 CKB 接受中文自然语言有什么区别，怎样公平比较？

### 选中文本

> 人工设计关键词与 CKB 中文自然语言

### 解释

#### 人工设计关键词与 CKB 中文自然语言：区别与公平对比

##### 核心含义

这里比较的不是两个输入完全相同的底层搜索算法，而是两种完成“从问题找到代码”任务的导航工作流：人工先把需求翻译成源码中可能出现的关键词，再交给 `grep` 做字面或正则匹配；CKB 则直接接收中文自然语言问题，利用已建立的知识索引返回候选源码、知识页和预算化 Agent pack。

两者最大的区别是**输入中包含的先验信息不同**。人工设计关键词已经注入了查询者对命名、框架术语和实现位置的猜测；中文自然语言主要表达任务意图，不保证包含源码中的真实标识符。因此，把人工看过答案后挑出的精准符号交给 `grep`，再把模糊中文问题交给 CKB，所得结果只能说明两套任务导航方案在各自输入条件下的实用性，不能直接证明某个底层检索算法更优。

本次 Agent pack 也提示了这一边界：候选项给出的选择原因是 `builder`、`ckb`、`code`、`knowledge` 等确定性词项，并把多个相关模块与知识页压缩进阅读预算；部分内容还因预算被截断。这说明“接受中文自然语言”描述的是用户入口与导航流程，不等于 CKB 只使用纯语义或向量算法，也不保证一次就命中精确函数。pack 未标记 `needs-source-read`，因此本解释不再扩展读取源码。

##### 在当前上下文中的作用

这句话用于限定面试手册中实验结论的口径：实验应回答“在不知道源码词汇时，哪种工作流更快把学习者带到正确区域”，而不是笼统回答“CKB 是否全面胜过 `grep`”。CKB 的价值侧重意图入口、候选压缩和关系导航；`grep` 的优势侧重已知词形后的精确落点。实践中二者可以串联：先用 CKB 缩小范围，再在指定路径内用精确符号查询核验。

##### 容易误解的边界

1. **`grep` 的关键词不是零成本输入。** 关键词由人设计时，应把阅读题目、猜测术语、改写查询和多轮尝试的时间计入工作流成本。
2. **CKB 接受中文不等于理解必然正确。** 自然语言仍可能被词项、索引质量、知识页覆盖和排序规则影响；文件级命中也不等于符号级命中。
3. **不能用事后关键词制造优势。** 如果人工先查看目标文件，再抽取真实函数名给 `grep`，就泄漏了答案；反过来，强迫 `grep` 直接匹配完整中文句子也会故意让它做不擅长的任务。
4. **导航效果不等于算法优劣。** 响应时间、Top-K 召回、阅读量、索引构建成本和最终答案正确率是不同指标，必须分别报告。

##### 简短例子

假设目标实现是：

```python
def revoke_refresh_token(token_id):
    ...
```

学习者只知道“用户退出后，在哪里让长期登录凭证失效？”。CKB 可以直接接收这句中文；人工关键词方案可能先设计 `logout`、`token`、`revoke` 等查询，再调用 `git grep`。如果把已经知道的 `revoke_refresh_token` 直接交给 `grep`，它是在做精确落点；CKB 收到的中文却是在做意图发现，两者不是同难度输入。

##### 公平对比方案

采用预注册的双轨、配对、盲测方案：

- **意图发现轨**：两边起点都是同一条不含路径、真实符号和源码原词的中文问题。CKB 直接查询；`grep` 组允许独立受试者在不知道答案的前提下设计关键词，但预先固定时间、查询次数和正则规则，并计入人工改写成本。比较目标文件 Recall@8、首次命中时间、查询次数、打开文件数和可见阅读量。
- **精确落点轨**：两边都获得同一个真实标识符，再比较符号或行级召回、误报数和延迟。这一轨单独检验 `grep` 的核心能力，不能与意图发现轨混成一个总分。
- **统一控制变量**：冻结相同提交、CKB 索引版本和目标答案；使用同一硬件；冷启动与热启动分开；限制相同候选文件预算；随机化题序并重复多轮，报告中位数与 P95。`grep` 没有天然相关性排名时，不应强套 Recall@8，除非预先定义确定性排序，否则报告“检查到第几个文件首次命中”。
- **公开完整成本**：分别报告索引构建、存储与常驻资源、人工关键词设计时间、阅读 tokens、文件级召回、符号级召回和最终答案正确率。

公平结论通常不是单一胜负：它应分别说明“未知源码词汇时谁更擅长导航”与“已知精确符号时谁更可靠地落点”，并进一步验证“CKB 导航 + 窄范围精确查询”的组合是否降低总耗时和阅读量。

本节依据当前 Agent pack 的预算化检索证据，并回链至 [[render_integration 与 harness_retrieval_contract 的协作实现]]、[[record_note 与 page_tag 的协作实现]]。

### 我的问题

现代 Agent 通过什么方法根据自然语言构建 grep 关键词？

### 选中文本

> 大仓库里，业务意图通常不是源码符号。单纯 grep 对已知符号很快，但面对“修改会话停止后的记录逻辑”这类问题，工程师需要自己构造关键词、阅读很多文件并恢复调用关系；直接把全仓 Markdown 或源码交给 Agent，又会增加 token 成本和决策波动。

### 解释

核心含义：现代 Agent 通常不会把整句自然语言直接当作一个 `grep` 关键词，而是先做**查询规划与词项展开**：从问题中拆出对象、动作、状态和结果，再生成可能出现在源码中的英文标识符、同义词及领域术语。例如把“会话停止后的记录逻辑”拆成 `session`、`stop`、`end`、`record`、`event`、`ingest`，然后组合搜索，并根据首轮命中的文件名、函数名继续收窄。

在当前上下文中，CKB 用确定性检索降低了这种“临时猜关键词”的不稳定性：自然语言问题先被转换为词项，在 SQLite 机器知识库中匹配文件、源码标识符、中文职责和实体全文；命中后再结合 Tree-sitter 提取的实体关系、LSP 证据及知识页定位相关源码。Agent 因而优先阅读预算化的候选集合，而不是遍历全仓或把所有内容塞进上下文。

容易混淆的边界是：`grep` 本身只做字面匹配，不理解业务语义；真正完成自然语言到关键词映射的是 Agent 的查询分解、同义词扩展或预建知识索引。Agent 生成的词也只是候选，不能仅凭命中次数断定实现位置，还需通过实体关系、调用关系或源码证据验证。CKB 展示的“纯确定性 Agent 检索”强调结果可复现，并不等同于完全依赖大模型进行开放式语义搜索。

简短例子：查询“修改会话停止后的记录逻辑”时，可先搜索 `session stop record`，再扩展为 `session end event ingest`；若命中 `ingest_event`、`start_session` 或 `automation.py`，就以这些真实符号为锚点继续追踪相关实体和调用关系。

## 历史记录迁移 · 检索词项由脚本还是 LLM 构造

### 我的问题

当前项目检索的词项构造是通过脚本还是 LLM？

### 选中文本

> 大仓库里，业务意图通常不是源码符号。单纯 grep 对已知符号很快，但面对“修改会话停止后的记录逻辑”这类问题，工程师需要自己构造关键词、阅读很多文件并恢复调用关系；直接把全仓 Markdown 或源码交给 Agent，又会增加 token 成本和决策波动。

### 解释

当前项目的检索词项由脚本按确定性规则构造，不是由 LLM 临时生成。`scripts/ckb_core/machine_knowledge.py` 实现 SQLite 机器知识库及纯确定性 Agent 检索；检索结果中的 `agent`、`builder`、`code`、`knowledge` 等“确定性词项”就是脚本提取和匹配的产物。

在当前上下文中，这套机制用于替代人工反复猜关键词：脚本从问题、选中文本及索引字段中提取词项，再完成匹配和候选页面选择；LLM 主要负责阅读 Agent pack 并生成面向人的解释，不决定首轮检索词项和结果，因此相同输入通常能得到稳定、可审计的检索过程。

容易混淆的边界是：用户或 LLM 可以改变输入问题的措辞，从而间接影响脚本能够提取哪些词项，但这不等于 LLM 在检索阶段自行扩写关键词、恢复调用关系或自由决定排名。

例如，输入“当前项目检索的词项构造是通过脚本还是 LLM”后，脚本确定性提取并匹配相关词项，找到 `machine_knowledge.py` 等候选；LLM 随后只根据生成的 Agent pack 解释结论。

### 解释

核心含义是：脚本不会先把自然语言“理解”为某个源码符号，而是把请求及其文档上下文规范化为可重复计算的词项，再用这些词项查询 SQLite 索引。英文按单词拆分并统一大小写，例如标题中的 `Code Knowledge Builder Agent` 会形成 `code`、`knowledge`、`builder`、`agent`；中文则会产生相邻字符组成的词项，选中文本里的“文件并”因此可能产生 `件并`。

这些确定性词项负责召回候选知识页和源码边界，Agent pack 中的“选择原因”展示的正是实际命中的词项。后续流程再结合索引关系、排序和 token 预算压缩候选内容，从而避免人工猜测关键词，也不必把全仓内容直接交给 Agent。

容易混淆的是，词项只是词法检索键，并不等同于源码实体、业务语义或调用关系。`grep` 通常要求已经知道准确字符串；这里允许自然语言产生多个检索入口，但真正的实体关系仍需由知识页、源码索引或图关系补充。另外，“选择原因”只列出促成该候选命中的词项，不代表请求只生成了这些词项。

例如，“修改会话停止后的记录逻辑”可以产生“修改”“会话”“停止”“记录”“逻辑”等中文词项；系统先据此召回与会话维护、记录笔记相关的页面，再从候选结果中定位 `agent_maintenance.py` 或 `workspace_notes.py`，而不是直接假定请求中存在同名函数。

### 我的问题

为什么召回率这么低，与固定式脚本构建词项是否有关，尤其是在中文语境下

### 选中文本

> 精确符号召回为 40%

### 解释

核心含义：这里的“精确符号召回为 40%”表示，在预期应命中的源码符号中，检索只找到了约四成。它衡量的是精确符号命中能力，不等同于相关页面召回率，更不直接代表最终回答只有 40% 正确。

召回偏低很可能与固定式词项构建有关，中文语境会进一步放大问题。确定性脚本若主要依赖字面词项，就难以连接中文问题与英文代码标识符之间的语义。例如“机器知识检索”实际可能对应 `retrieve_machine`，而“召回率低”未必会直接出现在符号名或源码文本中。当前 Agent pack 也显示，候选文件多由 `builder`、`code`、`knowledge`、`中文`、`固定` 等宽泛词项选出：这些词能扩大候选范围，却不一定把真正相关的检索实现排到前面。

需要区分三个边界：

1. **确定性不等于低召回**：若维护了中文别名、符号拆词、同义词和实体关系，确定性检索同样可以有较高召回。
2. **中文问题不等于中文符号**：自然语言通常使用“召回、词项、固定式”等概念词，而源码使用 `retrieve_machine` 一类英文标识符，单纯字面匹配容易断裂。
3. **精确符号召回不等于整体检索效果**：系统可能没有直接命中目标符号，却通过其所在文件、知识页或邻接关系取得足够上下文；反过来，命中许多包含通用词的文件也不代表找到了正确符号。

简短例子：查询“固定式脚本构建词项是否导致中文召回低”时，固定词项可能只提取出“固定”“构建”“中文”，于是召回多个通用模块，却遗漏真正负责检索的 `retrieve_machine`。因此，40% 更像是在暴露“中文概念到英文符号的映射不足”，而不是单纯说明 SQLite 或确定性检索机制本身无效。

## 18:35:43 · 追问 · Code Knowledge Builder 秋招面试官拷问手册

来源：[[analysis/Code Knowledge Builder 秋招面试官拷问手册|Code Knowledge Builder 秋招面试官拷问手册]] · 阅览模式选中文本

执行器：Codex / gpt-5.6-sol

### 承接问题

为什么召回率这么低，与固定式脚本构建词项是否有关，尤其是在中文语境下

### 我的追问

那么是否可以加入llm慢路径，用于在召回质量不佳时使用精准召回，可以参考各类记忆系统设计

### 解释

可以，而且这正好补足上一轮指出的“中文概念到英文符号映射不足”。建议在 `retrieve_machine` 的确定性快路径之外增加受控的 LLM 慢路径，而不是用 LLM 完全替换 SQLite 检索。

可采用类似分层记忆系统的流程：

1. **快路径初检**：先执行现有确定性检索，保留低成本、可复现和可审计的优势。
2. **质量门控**：当没有命中显式符号、候选主要由 `code`、`builder` 等通用词产生、候选得分普遍偏低，或多个候选难以区分时，才进入慢路径。
3. **LLM 查询扩展**：让 LLM 把中文问题转成结构化检索意图、英文符号候选、同义词和关系线索。例如把“机器知识召回”扩展为 `retrieve_machine`、`machine_knowledge`、检索、排序、实体与邻接关系，而不是让模型直接猜答案。
4. **确定性二次召回**：使用扩展词项重新查询实体、源码页和关系图，避免模型绕过知识库。
5. **候选重排与校验**：LLM 可以比较有限候选的语义相关性，但最终结果仍应附带命中的实体、路径和选择原因；若缺少证据，就保留“不确定”状态。

这里要注意，LLM 慢路径提升的主要是**语义召回**，不天然保证“精准”。如果让它自由生成符号，反而可能产生不存在的标识符。因此应限制它只做查询改写、候选扩展和重排，并由确定性索引验证符号是否真实存在。还可以缓存“中文概念—源码符号”映射；经过验证的映射以后进入快路径，从而使慢路径逐渐沉淀为稳定记忆。

简短例子：快路径只从“召回质量不佳”提取出“召回”“质量”，未找到精确符号时触发慢路径；LLM 推断问题涉及机器知识检索，并提出 `retrieve_machine`。系统随后必须回到索引验证该符号，验证成功后再展开其邻接实体。这样既弥补中文表达与英文标识符之间的鸿沟，又不会牺牲 CKB 的确定性和可审计性。
