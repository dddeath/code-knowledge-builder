# Code Knowledge Builder 项目说明书结构与验收样例

标签：#类型/分析

# 修订结论

Code Knowledge Builder 的项目说明不再套用参考书的章节数量和固定段落公式。参考文章只提供一种更自然的说明方法：从一个真实问题开始，沿着问题所需要的顺序解释设计选择，在恰当的位置加入源码、数据、比较和边界。章节应该由 Code Knowledge Builder 自身的逻辑长出来，而不是为了模仿参考文本的外形而排列。

项目的核心也不只在于让 Agent 更快地检索代码。Code Knowledge Builder 面对的是两个同等重要、需求又明显不同的读者：

- Agent 需要完整、可查询、来源绑定、预算受控且结果可重复的机器知识；
- 人类需要可发现、可理解、可行动、可信任的中文导航，能够知道一个页面负责什么、什么时候从这里进入、下一步应该查看哪个修改或验证入口。

因此，正式说明的主线调整为：**同一份固定源码事实，如何同时变成 Agent 可以精确检索的机器知识，以及人类可以直接理解和行动的代码地图。** 机器层与人类层不是主次关系，也不是一份内容的两种文件格式，而是面向两类任务分别设计、分别验收的知识产品。

## 修订后的内容重点

### 人类友好是一条独立设计主线

人类友好不等同于 Markdown 排版整齐，也不等同于把机器实体翻译成中文。人类层要帮助读者完成四件事：

1. **可发现**：面对一个任务，知道应该从首页、职责导览、工作记录还是精确检索进入；
2. **可理解**：看懂页面产生什么结果、为什么与当前任务有关，以及关键流程和约束是什么；
3. **可行动**：从页面直接到达源码、相关调用、影响范围和测试入口；
4. **可信任**：知道结论来自哪个固定源码范围，当前经过什么审阅和完成门。

这也是人类层主动控制页面数量、关系数量和附录体积的原因。机器层可以完整保存全部实体，人类层却需要选择少量高价值入口；机器层展示关系类型和来源证据，人类层则要把它们改写成自然的阅读提示。两层使用同一事实基础，但承担不同任务。

### Agent 友好是一条机器工作主线

Agent 侧关注的是另一组问题：怎样在有限上下文中稳定命中目标文件和符号，怎样回到精确源码范围，怎样避免每次重新扫描整个仓库，怎样区分固定事实与活动工作树变化，以及怎样把分析、修改和会话证据继续积累下来。

`machine/knowledge.sqlite`、分节 FTS、fast/precise 检索、Graphify、Agent pack、来源范围和 token 预算共同解决这些问题。它们的目标是提供有界、确定、可追溯的任务上下文，而不是替代人类页面。

### 两条主线在审阅和完成门处汇合

确定性脚本决定实体集合、页面归属、关系裁剪、排序、预算和完成门；Agent 重新打开固定源码范围，写出简体中文的含义、职责、修改时机和来源说明。最终审计同时检查机器事实是否完整、检索是否可用、人类页面是否可读、双层投影是否一致、源码链接是否有效，以及工作记录能否继续被找到。

这条汇合点比单独强调“Agent 检索更快”更接近项目本身：Code Knowledge Builder 试图建立的是一套人和 Agent 都能使用、又能共同维护的代码知识基础设施。

## 修订后的说明方式

正式正文不再为每章预设十个固定段落。每章只保留三个稳定要求：

1. 先回答本章最关心的问题；
2. 说明设计如何产生读者可以观察到的结果；
3. 在结尾交代证据、代价和下一章需要补充的内容。

不同主题采用不同展开方式：

- 讲人类页面时，从读者任务、阅读入口、页面内容和行动路径展开；
- 讲机器检索时，从输入、候选、排序、预算和来源展开；
- 讲构建流程时，沿真实数据流说明每个阶段的输入和产物；
- 讲验证时，先固定问题和指标，再解释结果与边界；
- 讲设计历史时，围绕问题认识如何变化来组织，而不是罗列版本号。

段落长短随内容变化。核心判断可以单独成段，机制和例子可以连续展开，表格只用于字段一致的比较。整体语气保持直接、克制、解释性强，减少刻意制造的戏剧冲突和机械的章末悬念。

## 修订后的章节结构

### 前言：一份代码，两种读法

说明代码库本身已经保存事实，但事实的存在不等于人和 Agent 都能有效使用。引出项目的双读者定位、写作范围和阅读路径。

### 第一部分：为什么还需要代码知识库

#### 第 1 章：代码在那里，知识在哪里

从代码、测试、提交记录和设计理由分散在不同位置讲起，说明“能够搜索”与“能够理解和修改”之间的距离。

#### 第 2 章：人和 Agent 需要的不是同一张页面

比较人类阅读与机器检索的任务差异，确立双层知识库的设计前提。

### 第二部分：先建立可信的事实基础

#### 第 3 章：固定 Git 来源

解释 commit、blob、range、detached snapshot 和活动工作树如何共同保证知识来源稳定。

#### 第 4 章：从语法事实到语义证据

说明 Tree-sitter、语言服务器、源码范围、诊断和关系如何组成可重建的代码事实。

### 第三部分：同一事实如何服务两类读者

#### 第 5 章：机器知识库为什么追求完整

说明 SQLite 中的实体、关系、源码、章节、审阅和工作记录，以及完整保存与有界读取的关系。

#### 第 6 章：人类知识库为什么主动克制

说明少量中文页面、职责聚合、自然关系句、折叠附录、源码入口和测试入口如何降低认知负担。

#### 第 7 章：事实层、机器层与人类层

讲清三层的职责、重建关系、投影关系和各自完成条件。

### 第四部分：知识是怎样生成的

#### 第 8 章：确定性脚本负责选择

说明页面数量、实体归属、关系预算、排序和上下文预算为什么交给脚本。

#### 第 9 章：Agent 负责解释

说明审阅包、固定源码范围、中文职责、修改时机和来源核对如何形成可读说明。

#### 第 10 章：证据如何变成完成状态

沿分段构建、审阅、合并、投影和审计说明三个完成标记的来历。

### 第五部分：人和 Agent 怎样使用它

#### 第 11 章：人类如何找到、理解并修改代码

从首页、职责导览、工作记录、源码入口和测试入口走完一条人类任务路径。

#### 第 12 章：Agent 如何在预算内定位代码

从 `brief`、Agent pack、`entity`、`neighbors`、`source` 到窄源码读取，说明机器任务路径。

#### 第 13 章：两条路径如何在一次真实修改中汇合

用同一任务展示人类导航和 Agent 检索如何指向相同来源、影响范围和验证入口。

### 第六部分：知识如何持续积累

#### 第 14 章：分析、修改、实验和会话记录

说明稳定代码页与持续工作记录为什么分开，以及工作记录如何回链代码知识。

#### 第 15 章：Hook、反馈与跨 Harness 同步

按触发时机、采集字段、写入形式和后续投影解释自动记录与人工反馈闭环。

### 第七部分：怎样证明它值得信任

#### 第 16 章：机器检索、人类可读性和任务完成

分别说明召回、符号定位、上下文、延迟、可发现、可理解、可行动和可信任的验收方法。

#### 第 17 章：当前边界与设计原则

集中说明语言近似、符号召回、宿主差异和迁移边界，最后回到“确定性脚本与来源绑定解释”的工程分工。

### 附录

- 从固定源码到机器与人类知识库的完整数据流；
- 从一个问题到修改、验证和回滚的完整任务流；
- CLI、SQLite、目录、状态与完成标记参考；
- 已确认事实、分析判断和待核验内容对照。

## 修订后的验收样例

### 前言：一份代码，两种读法

每个代码库都已经保存了大量知识。类和函数说明系统能做什么，测试说明哪些行为必须保持，提交记录留下变化发生的时间，设计文档则保存了一部分选择理由。问题通常不是知识完全缺席，而是这些知识分散在不同文件、不同工具和不同时间里，只有熟悉项目的人知道怎样把它们重新拼起来。

对刚接手项目的人来说，这种分散首先表现为阅读困难。目录能够显示文件放在哪里，却很少说明应该从哪里开始；搜索能够找到名称，却不能直接告诉读者哪个结果负责当前行为；调用关系能够列出连接，却还需要人判断哪些连接会影响修改，哪些测试能够证明修改成立。

对 Agent 来说，困难有另一种形状。它可以在很短时间内打开大量文件，但上下文窗口有限，文件数量也不能代替正确的任务入口。如果来源版本、符号范围、关系和验证路径没有提前组织好，Agent 得到的往往是很多相关内容，而不是足以形成修改计划的那部分内容。

Code Knowledge Builder 同时从这两种困难出发。

机器知识库保存完整的文件、实体、源码范围、关系、诊断、审阅和工作记录，使 Agent 可以按问题检索，并在需要时回到精确来源。人类知识库则主动缩小可见内容，把同一批事实重新组织成少量简体中文页面：这一页负责什么，什么任务应该从这里开始，相关代码为什么值得继续查看，修改后应该进入哪个测试。

这两层有意采用不同的表达方式。机器层追求完整和可查询，人类层追求清楚和可行动；机器层保留内部标识和完整关系，人类层使用自然标题、职责说明和阅读链接。人类页面的克制没有减少底层事实，机器数据的完整也不会把实体清单直接推给读者。

真正把两层连接起来的是同一条来源链。页面选择、实体归属、关系预算和检索排序由确定性脚本控制，Agent 在固定源码范围内补充中文解释，最终审计再分别检查机器知识、人类页面和两者之间的映射。于是，人看到的说明和 Agent 取回的上下文虽然形状不同，指向的仍是同一份代码事实。

因此，Code Knowledge Builder 的核心并不是单独为 Agent 建一个更快的索引，也不是为人类生成更多文档。它要建立的是一套共同的代码知识基础：机器能够精确查找，人能够自然阅读，双方都能沿着来源、修改和验证继续工作。

下一章先从最基本的问题开始：既然代码、测试和提交记录都已经存在，为什么它们还没有自然地组成一套可用的项目知识？
