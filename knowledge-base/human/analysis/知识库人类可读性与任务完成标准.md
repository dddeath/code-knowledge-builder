# 知识库人类可读性与任务完成标准

标签：#类型/分析

## 结论

知识库的人类可读性不是页面是否整洁、中文或简短，而是目标读者能否在受控的时间、跳转和信息量内完成任务。完整标准应同时覆盖可发现、可理解、可行动和可信任；交付纯净度是基础门，不能单独代表任务可读性已经成立。

当前知识库已通过结构纯净度审计，并且全部六十七个生成页面都能从首页到达，最远为三次跳转。这说明页面没有孤立，基础导航完整。与此同时，关系列表、聚合标题和超长附录仍会增加读者判断入口、识别影响范围和选择验证路径的成本。因此，后续改进应从“页面是否合规”推进到“读者是否完成任务”，并用冻结任务集验证效果。

## 可读性的完整定义

| 维度 | 读者需要完成的判断 | 知识库应提供的内容 |
|---|---|---|
| 可发现 | 当前问题应从哪里进入 | 按任务组织的首页、职责导览和具有明确目的的链接 |
| 可理解 | 页面负责什么，为什么与当前问题有关 | 结果优先的概览、进入条件、关键流程和当前约束 |
| 可行动 | 应修改哪里，会影响什么，如何验证 | 源码入口、修改联动、验证场景和风险边界 |
| 可信任 | 结论来自哪里，当前是否有效 | 固定源码范围、审阅状态、完成门和适用边界 |

四个维度是共同条件。页面即使整洁，只要读者找不到入口、看不懂关系、不能形成修改计划或无法追溯来源，整体可读性仍未完成。

## 当前基线

当前人类层的 `readability-audit.json` 状态为 `passed`，六十七个生成页面全部能从 `INDEX` 到达，最大导航深度为三跳。这些结果证明当前页面结构、中文叙述、双链和源码入口满足已有完成门。

进一步的确定性统计显示：

- 六十七个生成页面中，有二十三个标题采用“X 与 Y 的协作实现”形状。这种标题保留了源码锚点，但部分页面仍需要读者先理解符号，才能判断页面职责。
- “相关代码”“谁会来到这里”和“相关测试”共包含一千一百二十五条可见关系，其中六百四十七条使用“实现时会用到”“会使用这里提供的行为”“继续浏览”或“可从这里进入”等通用句式，占比约百分之五十七点五。
- 三十八个可见关系组超过七项；最大的“谁会来到这里”包含四十一项，`scripts 职责导览` 的“相关代码”包含二十五项。
- 三十三个页面含内部细节附录，其中三个页面超过三十项；最大的附录包含六十七个辅助实现。
- 最长生成页面为一百三十七行。折叠标记能减少 Obsidian 首屏占用，但不会减少普通 Markdown、全文搜索或 Agent 阅读时的文本负担。

这些数据不表示当前页面错误，而是说明已有审计主要回答“内容是否合规、完整且纯净”，尚未直接回答“读者完成任务需要付出多少判断成本”。

## 主要问题

### 导航存在但信息气味不足

链接如果只说明“存在关系”，读者仍需要逐个打开页面才能判断价值。关系句应说明目标页面、关系作用和点击原因，例如指出某个调用方为什么会受到修改影响，或某个测试具体覆盖什么行为。

### 源码可识别标题与任务可理解标题之间需要平衡

标题必须保留稳定源码锚点，避免读者无法回到代码；同时还应表达页面职责。适合的方向是“源码锚点：人类职责”，并由确定性脚本控制页面归属、排序、冲突消解和文件名稳定性。Agent 只审阅职责短语，不决定页面数量和所有权。

### 折叠展示不等于降低信息负担

内部细节默认折叠适合图形界面，但完整内容仍进入 Markdown、搜索和可能的上下文。辅助实现应先按职责分组；超过固定阈值后拆分为附录入口，完整实体继续保存在机器层。

### 结构通过不等于任务通过

当前审计能够检查标题、标签、中文、源码链接、双链和机器字段泄漏，这些门应继续保留。可读性效果还需要固定任务验证，例如定位检索排序入口、确认页面标题规则的影响范围、找到自动化停止事件的待审阅路径，以及从修改入口到达对应测试。

## 目标页面合同

稳定代码页的首屏应回答三个问题：

1. 这一页负责产生什么结果；
2. 什么情况下应该从这里开始；
3. 下一步最可能查看哪个修改或验证入口。

页面后续内容按以下顺序展开：

1. 当前职责和进入条件；
2. 关键流程、输入输出和必须保持的约束；
3. 源码位置；
4. 按上游输入、核心依赖、下游调用、修改联动和验证覆盖分组的关系；
5. 按职责收纳的内部细节。

稳定事实页只呈现当前有效行为。变更、迁移、审计和回滚信息继续放在对应记录中；会话、调试和待审阅证据不进入稳定代码页。

## 可读性预算

以下数值适合作为实施前冻结的初始工程阈值，而不是已经通过验证的普遍结论：

- 首页到核心生成页面最多三跳；
- 单个可见关系组最多七个高价值入口；
- 超过十个辅助实现时按职责分组；
- 超过三十个辅助实现时拆分附录入口；
- 修改入口必须关联验证入口，并说明测试覆盖的行为；
- 通用关系句必须补充点击目的，避免只表达“存在关系”；
- 页面首屏必须同时给出职责、进入条件和下一步入口。

阈值应在改写页面生成器之前固定，避免根据结果反向调整通过标准。

## 分层验收

### 第一层：交付纯净度

继续执行现有标题、标签、中文叙述、源码链接、双链、机器字段隔离和完成标记检查。

### 第二层：结构与信息负担

新增关系组大小、附录大小、首屏字段、验证入口、通用关系句和职责分组检查。脚本负责数量、顺序、预算和完成门，Agent 负责来源约束下的中文职责说明。

### 第三层：导航可达性

确定性计算孤立页面、首页最大跳数、修改页到测试页的可达性，以及职责导览中的扁平入口数量。

### 第四层：任务行为

使用实施前冻结的问题集，记录目标页面和源码命中、验证入口命中、跳转次数、错误入口、回退次数和完成时间。只有事实正确性不低于当前基线，并且读者成本下降时，才把变化称为可读性提升。

## 实施顺序

1. 先把当前统计和任务集固化为基线；
2. 再扩充可读性审计，不立即改写所有页面；
3. 分别调整职责导览、关系句、标题和附录，每次只改变一个变量；
4. 在独立 staging 知识库中重新投影；
5. 使用相同任务集比较基线与新版本；
6. 通过结构门和任务门后再切换正式人类层。

这套顺序把“做得更好”约束为可测量的小步修改，避免把可读性讨论扩展成无边界的页面重构。

## 当前边界

本分析定义了人类可读性的目标、现状、初始预算和验收方法，没有改变页面生成器、页面配置或正式人类投影。所列阈值在实施前需要冻结，并通过同一任务集验证；当前结论不包含尚未测得的效果提升声明。

## 后续补充

### 现行标准：知识库可读性与任务完成门

以下标准替代前文仍标记为“实施前初始阈值”的部分。可读性不再只由页面形状和导航统计判断；机器检索、人类阅读、任务落点、验证证据和维护一致性必须共同通过。具体速度倍数只作为当前 Flask 基线，不外推为所有仓库的固定要求。

#### 标准一：先产生可行动结果

知识库入口必须先告诉读者或 Agent：

1. 当前任务应进入哪个文件、类、函数或职责聚合；
2. 为什么该入口与任务相关；
3. 下一步应查看哪个源码范围、依赖、调用方或测试；
4. 当前结论的来源和适用边界。

只返回匹配词、关系数量或页面列表不算完成。页面可读但无法形成修改或验证计划，也不算任务可读。

#### 标准二：机器层和人类层分别验收

机器层以完整、来源绑定和可查询为目标，必须保存全部实体、范围、关系、证据、章节、固定源码和持久记录。人类层以低认知负担为目标，只展示受控数量的类、函数或职责聚合页，辅助实体进入一句中文附录。

两层不得互相替代：

- 人类页少不代表机器事实可以缺失；
- 机器实体完整不代表人类页面已经可读；
- Markdown 可浏览不代表 Agent 应宽扫整个 vault；
- SQLite 检索快速不代表任务已经完成。

#### 标准三：人类页面合同

稳定代码页的首屏必须回答：

- 这一页产生什么结果；
- 什么任务应从这里开始；
- 最可能的下一步修改或验证入口是什么。

页面后续依次提供关键流程与约束、源码位置、按职责分组的关系、测试覆盖和内部细节。页面必须使用简体中文叙述、一个页面类型标签、自然标题、有效双链和可点击源码位置；不得暴露 stable ID、commit、blob、classification 或原始机器关系计数。

关系链接必须说明点击目的。只写“继续浏览”“会使用这里的行为”或“存在关系”而没有任务含义，不满足信息气味要求。

#### 标准四：机器检索完成门

每次检索效果验收都必须在运行前冻结问题、目标路径、预算、最大结果、方法顺序、重复次数和阈值。至少检查：

| 指标 | 现行门 |
|---|---:|
| 目标源码 Recall@8 | 不低于 90%，且不低于冻结词法或人工基线 |
| 结果确定性 | 100% |
| 非预期宽搜回退率 | 0% |
| 可见上下文减少 | 相对冻结宽扫或 grep 基线至少 40% |
| Agent pack | 不超过请求 token 预算，并含来源路径与范围 |
| 精确符号召回 | 必须单独报告，不得用文件召回替代 |

如果交付路径使用常驻 stdio，还需满足：

- 进程启动、第一次缓存未命中和稳态请求分别计量；
- 稳态请求 P95 不超过 150 ms；
- 正式请求静态缓存命中率为 100%；
- 结果签名、文件召回、符号召回、上下文和回退率与一次性路径一致；
- 格式错误只影响当前请求，`shutdown` 或 EOF 能干净结束进程。

冷 CLI 延迟和引擎延迟必须分开报告，不能把已启动进程内的引擎时间写成完整命令延迟。

#### 标准五：任务完成分级

不同任务使用不同完成证据：

| 任务 | 完成条件 |
|---|---|
| 定位任务 | 命中目标文件，并给出目标类、函数或进一步精确查询入口 |
| 分析任务 | 说明方法、原因、效果和边界，回链知识页并进入两个 SQLite 索引 |
| 修改任务 | 给出修改文件与符号、修改原因、实际测试结果、影响范围和可执行回滚 |
| 验证任务 | 冻结协议、原始记录、汇总、失败门和复验命令均可重新检查 |
| 知识库维护 | Human/Markdown 镜像一致，页面唯一，链接有效，两个 SQLite 完整且可检索，`agent-policy check` 通过 |

目标文件命中只是修改任务的必要条件。没有定位到具体符号、没有执行验证或没有说明回滚时，不得把真实修改任务标记完成。

#### 标准六：吸收外部方法的完成条件

吸收 LLM Wiki、Graphify 或其他项目的方法时，必须区分：

- 直接吸收的方法；
- 经过 CKB 来源契约改造的能力；
- CKB 独立实现的功能。

每项吸收能力至少需要源码入口、稳定输入输出、测试或审计门、量化作用和负面边界。功能名称出现在文档中、页面能够生成或命令能够启动，都不等于吸收完成。

速度、上下文、可读性和任务成功率分别计量。双链、Obsidian、持久记录和页面审计主要改善导航与维护；FTS5、批量 SQL、缓存和常驻进程才直接影响毫秒级延迟，不把两类收益混为一个“性能提升”。

#### 当前 Flask 验证基线

当前同轮 Flask 3.1.3 十题结果为：

- 常驻机器检索中位延迟 24.9 ms，P95 47.6 ms；
- `git grep` 中位延迟 73.2 ms，P95 86.3 ms；
- 常驻检索中位速度为 grep 的 2.94 倍，延迟减少 65.9%；
- 可见上下文从 11,228 tokens 降到 2,294 tokens，减少 79.6%；
- 两者目标文件 Recall@8 都是 100%；
- 常驻检索精确符号召回 40%，grep 为 100%。

这些数字证明当前固定仓库上的任务级导航和上下文收益。由于 grep 使用人工关键词而机器检索使用中文自然语言，符号召回差异继续作为限制保留。完整归因和证据见 [[LLM Wiki 吸收特性与 Flask 检索收益]] 与 [[常驻 stdio 检索性能复测（Flask 3.1.3）]]。

#### 现行交付判断

只有以下项目同时成立，才将知识库任务标记完成：

1. 固定来源事实和审阅门通过；
2. 机器检索满足冻结质量、上下文和延迟门；
3. 人类页面满足首屏、导航、关系和源码入口合同；
4. 当前任务的定位、分析、修改或验证证据完整；
5. 页面、镜像、元数据和两个 SQLite 索引一致；
6. 失败结果和未覆盖指标没有被完成状态掩盖；
7. 回滚在隔离副本中执行并验证。

这套标准把“知识库存在”“页面合规”“检索快速”和“任务完成”分成连续但互不替代的验收层。
