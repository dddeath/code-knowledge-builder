# Code Knowledge Builder 秋招面试官拷问手册

标签：#类型/分析

## 结论与使用方法

这份手册用于准备 Code Knowledge Builder（下文简称 CKB）项目的秋招技术面试。准备目标不是背诵功能清单，而是形成一条可以经受连续追问的证据链：**为什么要做 → 约束是什么 → 怎样分层设计 → 为什么这样取舍 → 如何验证 → 哪些结果仍有边界 → 下一步怎样改进**。

推荐按面试时间使用：

1. **面试前快速复习**：先读“一句话、三分钟和十分钟项目介绍”，再读“核心设计取舍速查”和“量化结果与证据边界”。
2. **系统设计面试**：按“需求与约束 → 总体架构 → 数据与状态 → 检索 → 可靠性 → 验证”顺序展开。
3. **面试官连续追问**：使用后文六十道问题。每题先说“回答主干”，对方继续追问时再展开“深挖点”；项目现阶段存在不足时，直接使用“改进方案”，不要回避边界。
4. **简历投递前**：只使用自己能解释、能复现、能指出证据位置的数字；第三方组件与个人实现必须分开表述。

## 一句话、三分钟和十分钟项目介绍

### 一句话介绍

CKB 是面向代码 Agent 和工程师的多语言代码知识基础设施：它从固定 Git 快照提取完整、可追溯的代码事实，用确定性 SQLite 与图检索把自然语言任务压缩成预算内的源码入口，同时生成受控数量、简体中文、可直接导航的人类知识页。

### 三十秒介绍

未知仓库中的代码 Agent 常遇到两个问题：直接宽搜会加载过多无关上下文，而让模型自由总结整个仓库又会产生不稳定的页面归属和检索结果。CKB 用 Tree-sitter 获取统一语法结构，用语言服务器补充语义证据，把事实层、机器检索层和人类阅读层分开；分类、排序、配额、关系预算和完成门都由脚本确定，Agent 只在固定源码范围内写中文解释。查询阶段使用 FTS5、固定权重图传播和 token 预算，先定位文件与职责，再通过精确实体或源码范围命令落到函数。

### 三分钟介绍

**问题。** 大仓库里，业务意图通常不是源码符号。单纯 `grep` 对已知符号很快，但面对“修改会话停止后的记录逻辑”这类问题，工程师需要自己构造关键词、阅读很多文件并恢复调用关系；直接把全仓 Markdown 或源码交给 Agent，又会增加 token 成本和决策波动。

**核心约束。** 项目要求来源可追溯、构建可恢复、检索可重复、人类页面可读，并且活动开发不能污染长期基线。于是系统不能把“模型觉得重要”当作稳定结构，也不能用页面少来换取机器事实缺失。

**设计。** 系统先锁定干净 Git 提交和 blob/range 来源，用 Tree-sitter 抽取跨语言语法实体，用 Pyright、TypeScript Language Server、clangd 或 csharp-ls 提供语义证据；然后形成事实层 `facts/`、机器层 `machine/knowledge.sqlite` 和人类层 `human/`。完整实体和关系留在机器层，人类层只投影类、函数或职责聚合页，辅助实现进入一句中文附录。

**确定性。** 页面选择、附属实体归属、排序、配额、关系裁剪、检索权重、同分规则和审计门由脚本固定。Agent 重新打开精确源码范围，补写中文含义、职责、修改时机和来源核对，但不重新决定重要性。这样把模型不确定性限制在可审阅的叙述层。

**检索。** `fast` 使用标识符与中文词项、SQLite FTS5、固定元数据权重和有界两跳图传播；`precise` 增加固定源码全文检索和固定轮次加权 PageRank。结果严格受 token 预算和最大页面数限制，并携带源码路径与范围。精确符号任务再使用 `entity`、`neighbors` 或 `source`，而不是回到全仓宽搜。

**验证。** 截至本文记录时，自身知识库只读覆盖检查返回 31 个文件、483 个实体、1,985 条关系，483/483 实体已审阅，SQLite 完整性正常。独立的 5.1.4 冻结基准中，`machine-fast` 两轮目标源码 Recall@8 均为 100%，上下文相对 Markdown 宽扫减少 80.43%，中位延迟约 20.85–21.20 ms，零回退且跨进程结果一致；但辅助符号召回只有 16.67%，因此结论只覆盖“用较少上下文定位目标源码路径”，不等同于真实修改任务已经完成。

**取舍。** 项目不宣称全面替代 `grep`。Flask 3.1.3 的十题实验中，常驻检索与人工 `git grep` 的目标文件 Recall@8 都是 100%，常驻检索把可见上下文从 11,228 tokens 降到 2,294 tokens，中位延迟约 24.9 ms，而 `git grep` 约 73.2 ms；但精确符号召回为 40%，低于 `grep` 的 100%。推荐工作流是先用 CKB 定位文件、职责和相邻关系，再用精确符号查询或窄范围 `grep` 落点。

### 十分钟展开顺序

1. **先画边界**：输入是固定 Git 快照，输出是事实、机器、人类三层，活动工作树作为独立 overlay。
2. **再画主链路**：`detect → extract → build → cluster → review → merge → finalize`。
3. **解释两类消费者**：Agent 需要完整、预算化、来源绑定的机器检索；人类需要少页面、中文职责、明确修改与验证入口。
4. **解释确定性分工**：脚本决定结构和预算，Agent 只做精确来源上的解释与审阅。
5. **解释检索算法**：词项与锚点召回种子，固定权重排序，图扩展，预算裁剪，窄接口二次定位。
6. **解释生命周期**：分段状态、断点恢复、精确 blob 迁移、活动会话与变更记录、三重完成门。
7. **最后给数字与边界**：分别报告文件召回、符号召回、上下文、延迟、构建成本和下游任务尚未验证的部分。

## 项目问题、需求和非目标

### 要解决的问题

- 自然语言任务与源码标识符之间存在词汇差距。
- 宽范围搜索容易暴露大量无关文件和源码片段，增加 Agent token 与人工判断成本。
- 单一 Markdown 知识库难以同时满足机器完整召回和人类低认知负担。
- 让 Agent 自由决定“哪些实体重要、页面怎样归属”会导致重复构建结果漂移。
- 长构建和逐实体审阅中任一阶段失败，都可能造成大规模返工。
- 活动工作树持续变化，不能悄悄改写已经审计的固定基线。
- 会话和修改记录需要自动采集，但原始对话不能未经审阅直接进入稳定人类知识层。

### 功能需求

1. 支持 C、C++、C#、标准 JavaScript 和 Python 的代码事实提取。
2. 所有实体、关系、说明和源码范围可追溯到固定来源。
3. 支持全仓、路径范围和入口扩展三种扫描边界。
4. 构建可分段、可恢复、可审计，并在失败后只重跑必要阶段。
5. Agent 能通过自然语言获得预算内的相关页面、实体和源码入口。
6. 人类页面使用简体中文，控制数量和信息密度，并能形成修改与验证计划。
7. 可变分析、变更、实验、踩坑和会话记录能长期保留，不被生成器覆盖。
8. 自动化事件具备显式项目登记、会话级激活、脱敏、幂等和人工审阅门。

### 质量属性

| 属性 | 设计响应 | 验证方式 |
|---|---|---|
| 正确性 | 固定 commit、blob、精确 range、语义提供器证据 | 来源范围复核、关系端点审计、提供器诊断门 |
| 可重复 | 固定权重、固定轮次、固定排序、无随机采样 | 重复查询结果签名一致 |
| 可恢复 | 解析批次和审阅包独立保存 | 中断后从失败阶段继续 |
| 可读性 | 机器与人类投影分离，首屏结果优先 | 导航、关系、信息负担和冻结任务门 |
| 可维护 | 生成器只拥有清单内文件，可变笔记独立 | 镜像、元数据、双索引和策略审计 |
| 性能 | FTS5、批量 SQL、缓存、常驻 stdio、预算渲染 | P50、P95、上下文 tokens、缓存命中 |
| 可回滚 | 原始哈希、变更清单、补丁、隔离探针 | 回滚后字节与基线一致 |

### 明确非目标

- 不把任意网页、论文或对话直接当作源码实体写入固定事实图。
- 不用向量模型替代当前确定性检索，除非冻结 benchmark 证明下游质量与成本收益。
- 不把人类 Markdown 页面当作完整事实数据库。
- 不把文件召回率包装成精确符号召回或代码修改成功率。
- 不自动初始化非 Git 目录；只有用户明确选择后才建立一次初始提交。
- 不让自动化 Hook 阻塞 Harness 正常工作，也不把原始会话直接晋升为稳定知识页。

## 总体架构和数据流

```text
干净 Git 提交
    │
    ├─ 固定 blob/range 与 detached snapshot
    │        │
    │        ├─ Tree-sitter：跨语言语法实体
    │        └─ LSP：定义、引用、诊断等语义证据
    │
    ├─ detect → extract → build → cluster
    │        │
    │        ├─ facts：可重建事实与计数合同
    │        ├─ machine：完整 SQLite、FTS、关系、源码、记录
    │        └─ review packs：限定源码范围的 Agent 中文审阅
    │
    ├─ merge → finalize → 三重完成门
    │        ├─ human：保守中文知识页
    │        └─ markdown：兼容镜像
    │
    └─ retrieve / entity / neighbors / source / changes
             └─ 预算内 Agent pack 与精确源码入口

活动工作树 ──> overlay / session / change / automation pending review
```

### 三层数据职责

| 层 | 保存什么 | 为什么单独存在 | 不能替代什么 |
|---|---|---|---|
| `facts/` | 图、来源清单、审阅清单、计数合同 | 保证机器库可重建，固定审计边界 | 不能直接作为人类文档 |
| `machine/knowledge.sqlite` | 全部实体、范围、关系、证据、源码、中文章节、记录与 FTS | 为 Agent 提供完整、可查询、预算化的知识 | 不能用“完整”证明人类可读 |
| `human/` 与 `markdown/` | 受配额控制的中文页面和长期人工记录 | 降低人的阅读与导航成本 | 不能用“页面少”证明事实完整 |

### 固定基线与活动工作树

固定快照回答“这条知识基于哪一版源码”；活动工作树回答“当前正在改什么”。语义提供器始终读取 detached 基线，活动变化进入 overlay 或变更记录。这样既允许构建期间继续开发，也防止尚未审阅的修改污染完成标记。

### 构建状态机

1. `init` 完成 Git、范围、运行时和配置预检，并建立固定快照。
2. `build-chunk` 分批解析语法与语义事实。
3. `review-pack` 要求 Agent 重开指定源码范围并写中文说明。
4. `audit` 检查批次内部实体、关系、来源、中文和边界。
5. `merge` 解析跨批次关系并生成完整图。
6. `finalize` 生成机器、人类投影并执行全局完成门。
7. 只有固定事实、机器层、人类层和格式门全部通过，才写入三个完成标记。

## 基础概念速查

### 抽象语法树与 Tree-sitter

抽象语法树（AST）把源码文本转换成有层级的语法结构，例如函数、类、参数和调用表达式。Tree-sitter 是增量语法解析器，优点是多语言接口一致、容错强、适合批量提取；局限是它主要知道“语法长什么样”，不总能可靠判断跨文件符号真正指向谁。

### 语言服务器协议

语言服务器协议（LSP）把编辑器与语言语义服务解耦，可提供定义、引用、符号和诊断。CKB 使用 LSP 补足 Tree-sitter 的跨文件语义，但不会把任一提供器结果当作无条件真值；协议失败、致命诊断、合法空结果和近似模式必须分开记录。

### Git commit、blob 和源码范围

commit 固定仓库状态，blob 固定单个文件内容，range 固定声明所在行区间。三者共同形成来源证据。只存路径不够，因为同一路径在不同提交中可能表示不同实现；只存 commit 也不够，因为面试或修改定位需要落到具体文件与范围。

### 知识图谱

知识图谱用节点表示文件、类、函数等实体，用边表示定义、引用、调用、包含或测试覆盖等关系。CKB 的图用于有限关系扩展和职责群导航，不直接把完整图倾倒成人类页面。

### SQLite FTS5

FTS5 是 SQLite 的全文检索模块。CKB 对实体名、限定名、中文职责、章节和固定源码建立索引，优点是本地、可复现、易做事务与完整性检查；不足是纯词法检索仍存在同义词和精确符号歧义，需要固定词项归一、元数据权重和图关系补充。

### PageRank 与有界图传播

PageRank 根据图连接关系迭代分配重要性。CKB 的 `precise` 使用固定轮数、固定重启率和固定权重，保证同一输入产生同一结果；`fast` 则采用有界两跳传播，减少跨模块计算。两者都只是排序方法，不是正确性证明。

### token 预算

token 预算限制返回给 Agent 的可见上下文。系统先排序候选，再在预算内保留紧凑目标和必要章节；长章节超预算时截断章节，而不是静默丢掉整个目标。预算控制的是消费成本，不应改变底层事实完整性。

### Recall@8 与精确符号召回

Recall@8 表示前八个候选是否包含预先定义的相关目标。文件 Recall@8 回答“应修改的文件是否出现”，精确符号召回答“具体函数或类是否出现”。二者必须分别报告；文件召回 100% 不代表已经定位到函数，更不代表修改成功。

### P50、P95 与冷启动

P50 是中位延迟，P95 反映较慢请求的尾部体验。完整 CLI 延迟包含进程启动、数据库打开和渲染；常驻 stdio 的稳态延迟复用进程和缓存。面试中必须分别报告冷启动、首个缓存未命中和稳态请求，不能只挑更好看的数字。

### 确定性、幂等与原子性

- **确定性**：同一输入、状态和配置得到相同排序与输出。
- **幂等**：同一事件重复提交不会生成重复会话、轮次或记录。
- **原子性**：一次状态替换要么完整成功，要么保持旧状态，避免半写入。

### spool、WAL 和 checkpoint

spool 是先落盘、后处理的写前队列，用于中断恢复；WAL 是 SQLite 的预写日志模式，允许更稳健的事务与并发读取；checkpoint 把阶段进度和输入证据固定下来，避免失败后从头扫描。三者解决的层次不同，面试中不要混为一个概念。

### 投影、镜像和生成器所有权

投影是从机器事实生成面向特定读者的视图。`human/` 是人类投影，`markdown/` 是兼容镜像。生成器只替换清单中自己拥有的文件，人工分析、变更和编辑器工作区保持独立，避免重建知识库时丢失长期知识。

### canary、审计门和完成标记

canary 是小范围真实链路探针；审计门是可重新计算的验收规则；完成标记只是审计通过后的结果文件。命令退出成功、文件生成或标记存在都不单独等于任务完成，仍需核对目标行为和证据。

## 核心设计方法与设计理念

### 方法一：先固定边界，再讨论智能

源码版本、路径范围、语言提供器、页面配置、token 预算和验收题集先固定，模型只在边界内工作。这样失败时能判断是来源、解析、排序、审阅还是验证问题，而不是把所有偏差归因于“模型不稳定”。

### 方法二：完整事实与低认知负担分离

机器层追求不丢事实，人类层追求只显示高价值入口。把两者做成同一个页面集合，会在“完整但难读”和“简洁但信息丢失”之间反复摇摆。三层设计把矛盾变成两个独立验收目标。

### 方法三：脚本掌握结构，Agent 掌握解释

重要性、归属、排序、配额和完成门适合确定性程序；职责解释、修改时机和关系意义需要理解源码上下文，适合 Agent。分工不是排斥模型，而是把模型放到可审阅、可追溯的部分。

### 方法四：证据先于叙事

每个项目亮点先确定输入、命令、原始记录、结果和失败门，再组织简历与面试表达。只要一个数字不能回到冻结协议和原始记录，就不应写成普遍效果。

### 方法五：任务完成优先于页面合规

中文、标签、双链和源码链接是基础门；真正的人类可读还要求读者能找到入口、理解职责、形成修改方案并找到验证路径。页面结构通过不能替代真实任务行为验证。

### 方法六：失败局部化与可恢复

解析批次、语义提供器、审阅包、合并和投影各自保存状态。失败只重跑受影响阶段；迁移只复用路径、语言、blob 和旧状态完全匹配的事实。这样控制大型仓库的时间和上下文成本。

### 方法七：默认保守，效果通过 benchmark 赢得

向量检索、更多页面、自动晋升和复杂缓存都可能改善某个局部指标，也可能引入成本和不可解释性。项目先选择本地、确定性、可审计方案；新能力必须在冻结协议下证明下游收益，再进入主路径。

### 方法八：把负面结果作为设计输入

精确符号召回不足、构建审阅成本较高、冷启动比 `grep` 慢，都不是应隐藏的缺点。负面结果直接决定二阶段符号重排、常驻进程、增量迁移和下游 Agent benchmark 的优先级。

### 方法九：配置与完成门一起版本化

页面配额、可见章节、关系预算、上下文预算和审阅包预算不是运行时随意调节的展示参数，而是构建结果的一部分。初始构建会把规范化配置复制到输出并写入状态；恢复和最终审计继续使用同一份配置。这样可避免为了让结果通过而在构建中途改变配额，也让迁移、benchmark 和回滚能够比较同一合同下的结果。

## 核心设计取舍速查

| 设计问题 | 当前选择 | 选择理由 | 代价与补偿 |
|---|---|---|---|
| 语法还是语义 | Tree-sitter + LSP | 统一多语言结构，同时补充跨文件语义 | 工具链更复杂；用提供器证据和诊断门隔离 |
| 一个知识库还是三层 | facts + machine + human | 同时满足可重建、机器完整、人类可读 | 投影一致性成本；用计数、镜像和全局审计保证 |
| 模型排序还是固定排序 | 确定性脚本 | 可复现、可回归、可解释 | 语义泛化有限；保留 Agent 中文说明和后续 benchmark |
| 向量还是 FTS5 + 图 | 当前选择后者 | 本地、低依赖、无隐藏模型排序 | 同义词与符号歧义；用词项归一、锚点、二次精确查询 |
| 全量重建还是增量迁移 | 精确 blob 复用 | 只复用字节完全相同的事实与匹配审阅 | 变更文件仍需重建；换取来源可信度 |
| 活动仓库还是 detached 快照 | 固定快照做语义根 | 基线不受开发中修改污染 | 需要 overlay 表示当前变化 |
| 自动记录还是人工记录 | 自动采集 + 人工晋升 | 减少遗漏，又不让原始对话污染稳定知识 | 增加 pending review；用检索暴露待办 |
| 更多页面还是保守页面 | 配额与附录 | 降低人类导航负担 | 细节不在首屏；机器层保留完整事实 |
| 一次性 CLI 还是常驻 stdio | 两者并存 | CLI 简单，stdio 降低稳态延迟 | 生命周期更复杂；分别验证冷启动与稳态 |

## 模拟面试官拷问与回答

### 第一组：项目定位与需求

#### 1. 你这个项目到底是什么？不要念功能列表。

**回答主干：** 它是代码知识基础设施，核心不是“把源码生成 Markdown”，而是把固定源码事实转换成两种消费接口：Agent 使用完整、预算化、可追溯的 SQLite 与图检索；人类使用少页面、简体中文、能指向修改和验证入口的知识库。系统通过确定性脚本控制结构，通过 Agent 做来源绑定解释。

**深挖点：** 输入边界是 Git 快照，核心产物是三层数据，主要效果是降低未知仓库任务的上下文成本和检索波动。

#### 2. 为什么不直接让大模型把整个仓库总结一遍？

**回答主干：** 一次性总结缺少稳定来源、容易遗漏长尾实体，而且页面选择和归属会随模型变化。CKB 先确定性抽取完整事实，再让 Agent 只解释固定范围；结构决策可回归，叙述也能回到源码复核。

**改进方案：** 模型仍可用于生成职责说明或任务答案，但输出必须带来源范围，并通过记录接口进入可审阅层，而不是替代事实图。

#### 3. 你的目标用户是谁？

**回答主干：** 第一类是需要在未知仓库中定位修改入口的代码 Agent；第二类是需要理解职责、影响面和验证路径的工程师。两类用户的完整性与可读性目标不同，所以系统不强迫他们共用同一个信息视图。

#### 4. 这个需求是伪需求吗？工程师会用 `grep` 和 IDE。

**回答主干：** 已知符号时 `grep` 和 IDE 更直接，CKB 不替代它们。价值出现在“只知道业务意图、不知道文件和符号”的任务：先用自然语言把范围缩小到文件、职责和邻接关系，再交给符号工具精确落点。Flask 对照显示，文件级召回不退化且可见上下文明显减少，但精确符号仍应使用二次工具。

#### 5. 你如何定义项目成功？

**回答主干：** 分四层：固定事实与来源正确；机器检索在冻结题集上满足召回、确定性、上下文和延迟门；人类页面能形成修改与验证计划；真实任务最终有修改、测试和回滚证据。某一层通过不能代替下一层。

#### 6. 你明确不做什么？

**回答主干：** 不把任意外部材料混入源码事实层，不让模型自由决定稳定结构，不默认启用向量检索，不把原始会话直接写入人类知识页，不用文件召回冒充代码修改成功，也不自动改动非 Git 目录。

#### 7. 需求里最冲突的两个目标是什么？

**回答主干：** 机器需要完整事实，人类需要低信息负担。如果使用单一页面集合，完整会导致难读，压缩会导致事实丢失。三层设计把冲突拆成独立产物和独立完成门。

#### 8. 为什么强调“未知仓库”？

**回答主干：** 熟悉仓库的工程师已经有内部路径和符号记忆；未知仓库最能暴露词汇差距、上下文浪费和错误入口。benchmark 也应使用预先未知或冻结的问题，避免把作者记忆误当作检索能力。

#### 9. 这个项目最难的地方是什么？

**回答主干：** 不是解析一个函数，而是保持多层一致性：固定来源、语法语义事实、关系、页面归属、检索索引、中文审阅、可变记录和完成标记必须同时成立。任何“局部成功”都可能掩盖全局不一致，所以需要确定性状态机和多层审计。

#### 10. 如果只允许保留一个亮点，你保留什么？

**回答主干：** 保留“确定性脚本控制结构，Agent 只做来源绑定解释”的分工。它同时解释了为什么结果可重复、为什么中文说明仍有语义、为什么可做回归，以及为什么模型能力变化不会破坏基本数据边界。

### 第二组：解析、语义与来源

#### 11. 为什么使用 Tree-sitter？

**回答主干：** 它提供跨语言一致、容错较强的语法树，适合稳定抽取类、函数、参数和调用形状。相比正则，能更可靠处理嵌套和语言语法；相比只依赖某个编译器，跨语言接入成本更可控。

**边界：** Tree-sitter 不能独自可靠解决跨文件符号绑定和动态语言语义，所以还需要 LSP 与证据置信度。

#### 12. 既然有语言服务器，为什么还需要 Tree-sitter？

**回答主干：** LSP 在不同语言、项目配置和依赖状态下的覆盖与响应形状不同；Tree-sitter 提供稳定的语法骨架和完整声明枚举，LSP 提供定义、引用和诊断等语义增强。双通道允许在语义受限时明确降级，而不是整条流水线失效。

#### 13. Tree-sitter 和 LSP 结果冲突怎么办？

**回答主干：** 先把语法实体作为候选，再用语义提供器证据建立或修正关系；冲突不能静默覆盖，要保存提供器、诊断和置信类型。致命冲突阻止完成，非致命近似必须在审计中标记边界。

#### 14. 动态语言里的调用关系真的可靠吗？

**回答主干：** 不能把所有动态调用都当成精确关系。系统区分来源明确、推断和歧义关系，并保留提供器证据；人类页面只展示有任务价值且受预算控制的自然关系，机器图保存完整分类。

**改进方案：** 对高价值动态入口加入运行时 trace 或测试覆盖证据，但作为额外证据层，不篡改固定静态事实。

#### 15. 为什么必须是 Git 仓库？

**回答主干：** 知识结论必须绑定稳定来源。Git commit 和 blob 能确定文件字节，范围能定位声明；没有提交时，后续无法判断页面对应哪个版本，也无法可靠迁移和回滚。非 Git 目录只有在用户明确选择后才创建初始提交。

#### 16. 只保存 commit 不就够了吗？为什么还存 blob 和 range？

**回答主干：** commit 固定全仓状态，blob 允许判断单文件是否完全未变并支持增量复用，range 让 Agent 和人类直接重开证据位置。三者分别服务版本边界、文件级复用和精确复核。

#### 17. 固定快照会不会很快过时？

**回答主干：** 会，所以系统明确区分固定基线和活动 overlay。稳定知识回答“已审计版本是什么”，overlay 回答“当前工作树正在变什么”。要更新基线时走精确 blob 迁移和重新审阅，而不是悄悄覆盖旧事实。

#### 18. 为什么语义提供器读取 detached worktree？

**回答主干：** 如果提供器读取活动工作树，构建过程中用户修改文件会使同一批次前后看到不同源码，来源清单和语义关系无法复现。detached 快照把语义根固定，活动开发仍可继续，但通过另一条状态链记录。

#### 19. 合法空 `documentSymbol` 和提供器失败怎么区分？

**回答主干：** 空列表可能表示模块只有导入或顶层调用，是合法结果；真正失败应由请求异常、致命诊断、协议错误或致命 stderr 识别。项目曾把合法空结果误判为失败，后续把“空”与“错”拆开，并由独立覆盖门检查关键实体是否遗漏。

#### 20. 多语言如何统一，又如何保留语言差异？

**回答主干：** 统一层使用文件、类型、函数、方法、范围和关系等公共事实模型；语言适配层负责 AST 节点映射、提供器启动、项目选择和特殊语义。公共审计验证一致性，语言专项门处理 C/C++ compilation database、C# solution、Python 动态特性等差异。

### 第三组：三层知识库与人类可读性

#### 21. 为什么需要 `facts/`，直接从 SQLite 备份不行吗？

**回答主干：** SQLite 是消费层，包含索引和投影；`facts/` 是可重建的权威事实与计数合同。分开后可以验证数据库是否完整反映事实，也能在数据库格式升级时重建，而不把某个 SQLite schema 当作唯一真相。

#### 22. 为什么人类页不能一实体一页？

**回答主干：** 一实体一页对机器完整，但会制造大量薄页面、重复关系和导航噪声。人类层只让类、函数或职责聚合成为主页面，访问器、局部辅助函数和薄包装进入附录；机器层仍保存全部实体，因此压缩不等于删除。

#### 23. 页面配额由谁决定？为什么不让 Agent 判断重要性？

**回答主干：** 配额、归属、排序和冲突消解由脚本决定，因为这些结构需要跨运行稳定。Agent 只基于固定源码解释职责。若让 Agent决定页面数量，模型或提示变化会造成大规模无意义 diff，难以 benchmark 和迁移。

#### 24. 你说人类可读，怎么测？

**回答主干：** 分四维：可发现、可理解、可行动、可信任。基础门检查中文、标题、标签、双链和源码入口；任务门冻结问题，记录目标命中、跳转数、错误入口、回退、验证入口和完成时间。页面短或审计通过都不能单独证明可读。

#### 25. 为什么把简体中文设成硬门？

**回答主干：** 目标读者和长期知识库以中文为主；如果语言只是偏好，批量审阅很容易混入纯英文模板句，降低一致性和检索效果。硬门在审阅、全局图、机器层和人类层重复检查；代码标识符和必要术语仍保留原文。

#### 26. 中文硬门会不会妨碍国际化？

**回答主干：** 当前产品合同选择中文叙述以保证一个稳定读者群，并不等于底层事实只能中文。国际化应新增独立投影和语言门，而不是在同一页面随机混写；机器实体、代码符号和来源仍是语言中立的。

#### 27. 什么叫“关系链接有信息气味”？

**回答主干：** 链接文本应告诉读者为什么值得点击，例如“修改停止事件后应检查该测试的幂等行为”，而不是“继续浏览”或“存在调用”。链接数量受预算控制，关系句要表达上游、下游、影响或验证意义。

#### 28. 折叠附录不就解决信息过载了吗？

**回答主干：** 折叠只减少 GUI 首屏占用，Markdown 全文、搜索和 Agent 上下文仍包含内容。真正降负担需要先按职责分组、限制可见入口，必要时拆成附录入口；完整事实继续留在机器层。

#### 29. 为什么分析、变更、实验和会话不直接写进稳定代码页？

**回答主干：** 稳定代码页描述当前有效行为，过程记录描述为什么改、怎样验证和当时发生什么。混在一起会让页面随每次会话膨胀，也会把旧决策误读为现行事实。记录通过独立类型保存，并回链稳定代码页。

#### 30. 生成器重建时如何保护人工笔记？

**回答主干：** 生成器只替换清单中拥有的文件，分析、变更、实验、踩坑、会话和编辑器工作区不在覆盖集合。重建前后还可比较笔记哈希和 Human/Markdown 镜像，确认长期人工知识没有被投影覆盖。

### 第四组：检索与排序

#### 31. `fast` 检索具体怎么做？

**回答主干：** 先归一标识符、中文词项和精确锚点，用实体与章节 FTS5 找种子；再加入文件名、限定名、已审阅职责等固定元数据权重，对没有测试意图的问题降低测试实体权重；最后做有界两跳图传播、按源码路径去重，并在 token 和页面数预算内渲染。

#### 32. `precise` 和 `fast` 有什么区别？

**回答主干：** `fast` 面向日常定位，限制候选物化窗口和图扩展深度；`precise` 增加固定源码全文检索，并执行固定二十四轮加权 PageRank，适合跨模块问题。两者的权重、轮数、同分排序和预算都固定，因此都可重复。

#### 33. 为什么不用向量数据库？

**回答主干：** 当前目标首先要求本地、可解释、可重复和低依赖；向量模型会引入模型版本、嵌入成本、近邻索引和隐藏语义漂移。现有 FTS5 与图检索已经在冻结文件定位任务上通过门，所以向量检索被保留为待 benchmark 的候选，而不是默认复杂度。

**改进方案：** 如果后续同义表达召回不足，可增加向量候选通道，但排序融合、成本、缓存和离线可用性必须冻结，并以真实下游任务成功率证明增益。

#### 34. FTS5 只是词法匹配，中文自然语言怎么召回？

**回答主干：** 使用标识符拆分、CJK 词项和中文三元词项，索引不仅包含符号名，还包含 Agent 审阅的中文含义与职责；文件名、限定名和关系图提供额外固定权重。它仍不能覆盖所有同义词，所以精确锚点和二次查询必须保留。

#### 35. 图传播为什么只做两跳？

**回答主干：** 日常修改定位最需要直接依赖和相邻职责，传播过深会把大图高度连接节点带入结果，降低精度并增加成本。有界两跳是性能与局部语义的保守选择；跨模块问题再使用 `precise` 的固定迭代。

#### 36. 关系权重怎么定？

**回答主干：** 按关系类型的任务价值、来源置信和节点度数设置固定权重，并对高连接节点做惩罚，避免“谁都连接”的节点占据结果。权重必须写进代码和回归协议，而不是由查询时的 Agent 临时决定。

#### 37. token 预算不足时怎么办？

**回答主干：** 排序后先保留最终目标的紧凑区块，再按章节填充；某章节太长时截断章节，不跳过整个目标。返回结果公开估算 tokens、所选实体和截断情况。若没有可信来源候选，则返回 `needs-source-read`，只允许按返回路径做窄源码读取。

#### 38. 为什么需要 `entity`、`neighbors` 和 `source`，一个 `retrieve` 不够吗？

**回答主干：** `retrieve` 解决自然语言到候选范围；`entity` 解决精确符号；`neighbors` 解决有界影响关系；`source` 解决精确源码重开。把不同任务拆成窄接口，避免为找一个函数重新加载完整图或宽扫仓库。

#### 39. 缓存如何失效？

**回答主干：** 缓存键绑定数据库与本地 opener 的修改时间，实体元数据、章节、关系图和源码链接渲染器只在输入未变时复用；数据库原子替换或配置改变后，下一次请求重建。不能只按进程生命周期永久缓存，否则迁移或记录刷新后会读到旧结果。

#### 40. 为什么常驻 stdio 不开 HTTP 服务？

**回答主干：** 本地 Harness 只需要一进一出的 JSONL 协议，stdio 没有端口、鉴权和服务发现成本，生命周期随插件或会话管理。HTTP 适合多客户端或跨机部署，但会增加网络暴露和运维；当前需求不需要这层复杂度。

#### 41. CKB 与 `grep` 的正确组合是什么？

**回答主干：** 业务意图未知符号时，先用 CKB 找文件、职责、关系和验证入口；知道符号后，用 `entity`、`source` 或窄范围 `grep` 精确定位。`grep` 是强词法工具，CKB 是任务导航层，二者是分工而不是互斥。

#### 42. 精确符号召回低，是否说明项目失败？

**回答主干：** 说明当前完成边界是文件级任务导航，不是精确符号搜索。文件召回、上下文和确定性门已通过；符号召回作为独立短板公开保留。项目是否失败取决于预先定义目标，不能事后把未冻结指标包装成已完成。

**改进方案：** 在文件命中后，对函数签名、限定名、调用关系和测试意图做第二阶段确定性重排；保持相同 token 预算，用同一冻结题集复验符号召回和下游修改成功率。

### 第五组：性能、实验与证据

#### 43. 你的 benchmark 如何避免“为结果调题”？

**回答主干：** 在构建或优化前冻结问题、目标路径、预算、最大结果、方法顺序、重复次数和阈值；保存原始记录与汇总；优化后使用原协议复测，不能根据结果删除失败题或重定义门。

#### 44. 为什么使用 Recall@8？为什么不是 Top-1？

**回答主干：** Agent pack 本来就允许少量候选，Top-8 衡量目标是否进入可消费范围；Top-1 过于强调单一排序。与此同时应报告候选数量、精确符号召回和实际任务行为，避免 Top-8 掩盖排序质量。

#### 45. 为什么要重复九次或七次？

**回答主干：** 重复测量用于估计中位与 P95，并检查结果签名是否完全一致。一次最快结果没有代表性，尤其在 Windows 进程启动、文件缓存和 SQLite 缓存存在时。

#### 46. 为什么报告上下文 tokens，而不只报告延迟？

**回答主干：** 对代码 Agent 来说，检索命令快不等于整体任务成本低；返回过多源码会增加模型推理成本、延迟和注意力干扰。延迟、召回、上下文和下游成功率是不同维度，必须分别测量。

#### 47. Flask 实验公平吗？

**回答主干：** 它是实用对照，不是完全对称算法实验：`grep` 使用人工冻结关键词，CKB 使用中文任务。优点是接近真实工作流，缺点是查询构造成本不同。面试中应主动说明，并保留原始协议供复查。

#### 48. 构建需要九十多秒，值得吗？

**回答主干：** 是否值得取决于仓库复用次数和任务成本。构建是一次性或增量成本，查询是重复收益。需要通过多任务累计节省、迁移复用率和下游成功率计算盈亏平衡；不能只拿单次查询加速忽略建库成本。

#### 49. 你如何区分冷启动和稳态性能？

**回答主干：** 冷 CLI 包含 Python 启动、模块加载、SQLite 打开和静态缓存构建；常驻 stdio 分首个未命中和后续命中请求。实验分别记录三段，用户可见往返还要包含 Harness 写入和读取时间。

#### 50. 结果最可能受到哪些外部因素影响？

**回答主干：** 仓库语言、规模、符号命名质量、关系密度、问题类型、文件系统、操作系统缓存、语言服务器准备度、题集作者偏差和目标粒度。解决方法不是宣称普遍数字，而是多仓库分层报告并保留每个协议的边界。

#### 51. 如果新版本延迟更快但 Recall 降了，怎么决策？

**回答主干：** 召回是质量门，延迟是成本门。若预设协议要求 Recall 不低于基线，则不能用速度补偿质量下降；先回滚或局部修正。只有产品明确给出可交换的效用函数，才允许在冻结规则下做权衡。

#### 52. 为什么不直接用真实大模型修改成功率作为唯一指标？

**回答主干：** 大模型版本、采样和提示会增加实验噪声，难以定位检索器问题。先用确定性的文件/符号召回、上下文和延迟做组件门，再增加固定模型、固定提示、固定任务的端到端 benchmark。两层结合，既可诊断也接近真实价值。

### 第六组：可靠性、自动化和演进

#### 53. 长构建中断后如何恢复？

**回答主干：** 解析批次、审阅包、审计和合并各自保存状态与输入证据；恢复时核对配置、快照和已完成集合，只重跑失败阶段。不能只保存“进度百分比”，因为那无法证明已完成批次对应相同输入。

#### 54. 增量迁移如何保证不会复用错误事实？

**回答主干：** 只有路径、语言、Git blob 和旧解析状态完全匹配才复用；实体标识重新绑定目标提交，审阅还要匹配叙述字段形状。变化文件和 delta 包重新解析、重新审阅，最终仍执行当前版本全部审计门。

#### 55. 自动同步为什么需要“项目登记 + 会话激活”两个门？

**回答主干：** 项目登记表示长期允许该仓库接入，session 激活表示当前任务明确使用 CKB。双门避免仅安装插件就捕获所有会话，也防止工作区内无关任务被自动写入机器记录。

#### 56. Hook 事件如何避免重复和丢失？

**回答主干：** 事件先写入原子 spool，再规范化、脱敏和确定性去重，随后写入 `automation.sqlite`；事件、会话、轮次和路径都有稳定幂等键。中断后 `drain` 继续处理，失败项显式 `retry`，重复重放不生成重复记录。

#### 57. 为什么停止事件只生成 `pending-agent-review`？

**回答主干：** 原始或近原始会话可能包含临时推理、无关内容和敏感字段，不应直接污染人类知识。停止事件只形成机器层待审阅记录；Agent 重开全部变化路径，写中文正文、证据说明和精确路径集合后，才晋升为人类变更页。

#### 58. 自动化如何处理隐私和敏感信息？

**回答主干：** 入库前递归处理敏感键、授权头、凭据赋值、私钥文本和自定义模式，并限制字段长度；自动化只接受已登记项目和显式激活会话。安全边界还包括不解析 Harness transcript 文件、不扩大仓库路径范围、不阻塞正常工具执行。

#### 59. 三个完成标记有什么用？

**回答主干：** 总完成、机器完成和人类完成分别表达全局、机器事实/索引、人类投影通过。分开后能定位失败层；但标记本身不是证据，仍要重开审计 JSON、SQLite 完整性、目标页面和镜像。

#### 60. 如果让你继续做一个迭代，你会做什么？

**回答主干：** 优先做文件命中后的确定性符号二次重排，并建立固定模型的下游修改任务 benchmark。原因是当前文件级召回、上下文和稳态延迟已经有证据，最明显的质量缺口是符号召回；端到端 benchmark 能判断这个改进是否真正减少错误修改和回退。

**实施方案：** 冻结多仓库任务、目标符号、token 预算和模型；新增签名/限定名/局部调用权重；先做组件复验，再让同一模型完成修改、测试和回滚；比较成功率、误改文件数、二次检索次数、总 tokens 和墙钟时间。

## 系统设计加压题

### 仓库扩大到百万行代码怎么办？

1. 按语言、路径和职责边界分段，解析批次与审阅包独立 checkpoint。
2. 机器层完整保存，查询只物化固定 overscan 窗口，不随实体总量线性渲染。
3. 使用路径 scope、入口扩展和一跳边界支持局部建库；全仓构建与任务切片分开。
4. 迁移按 blob 精确复用，避免每次提交全量重审。
5. benchmark 增加索引大小、构建峰值内存、迁移复用率和尾延迟，而不只看查询中位数。

### 多仓库和 monorepo 怎么办？

项目登记保存 repo/output 对，workspace root 只做路由；直接仓库匹配优先，外层工作区命中时仍把 Git 状态和变化路径限制在嵌套源码仓库。跨仓依赖可作为显式边界关系，但不能把外部目录悄悄纳入来源图。

### 多个 Agent 并发读取和写记录怎么办？

读取使用 SQLite 和不可变事实，记录写入使用事务、原子替换与幂等键；自动化事件先进入 spool。人类投影更新需要串行化或乐观版本检查，冲突时保留待审阅状态，不允许两个 Agent直接手改生成器管理页面。

### 数据库损坏怎么办？

机器 SQLite 可以从 `facts/`、审阅记录和可变笔记重建；每次交付执行 `PRAGMA integrity_check`，保留原始哈希和完成门。恢复后还要验证实体、关系、章节、FTS 和人类归属计数，不能只验证数据库能打开。

### 语言服务器不可用怎么办？

先由 `doctor` 明确缺失运行时，不自动触发高成本 restore；支持的近似模式必须记录 precision 和 fallback evidence。关键语义门无法满足时停止完成，不能把 Tree-sitter 语法结果伪装成精确语义。

### 如何部署到团队环境？

优先把固定输出与源码提交绑定，通过只读机器库、独立人类 vault 和项目级 Agent 协议分发；Hook 需要项目登记和用户信任。版本升级采用 staging 迁移、全门审计、切换与回滚探针，不在生产目录上边跑边改 schema。

## 个人贡献与第三方边界

### 可以表述的个人贡献

- 设计并实现固定 Git 来源、三层知识库和活动工作树 overlay 的架构。
- 将 Tree-sitter 和多种语言服务器的结果映射到统一事实、来源与关系模型。

- 建立冻结 benchmark、原始记录、失败门、迁移、补丁、验证和回滚交付链路。
- 设计跨 Harness 的登记、会话激活、spool、脱敏、幂等与人工晋升流程。

### 必须明确的第三方能力

- Tree-sitter 提供语法解析基础。
- Pyright、TypeScript Language Server、clangd 和 csharp-ls 提供各语言语义能力。

### 当前简历项目描述

**Code Knowledge Builder｜多语言代码知识基础设施（个人项目）**

- 以固定 Git 提交为事实基线，融合 Tree-sitter/LSP 构建事实、机器检索和中文导航三层架构；确定性脚本约束实体归属与审计门，Agent 在精确源码范围内完成来源复核；基于 SQLite FTS5 与固定权重图传播生成 token 预算内源码入口。
- 在 Flask 3.1.3 中，常驻 CKB 与基于预设关键词的 `git grep` 基线目标文件 Recall@8 均为 100%；相比 `git grep`，CKB 将检索占用的上下文从 11,228 降至 2,294 tokens（减少 79.6%），并将 P95 延迟从 86.3 ms 降至 47.6 ms。

### 先讲清楚项目主线

这个项目解决的不是“怎样把整个仓库总结成文档”，而是“代码 Agent 面对陌生仓库时，怎样在可追溯、可复现和有限上下文内先找到应读的源码入口”。系统先把某个 Git 提交中的源码编译成可重建事实和完整机器索引，再把检索结果裁剪成带路径、源码范围、职责和关系的预算化阅读包；确定性脚本负责结构决策，Agent 只在脚本选定的精确来源上复核中文解释。它与 `git grep` 的关系是分工互补：CKB 先定位文件、职责和相邻关系，精确符号查询或窄范围 grep 再落到具体函数。

### 61. 什么叫“固定 Git 提交为事实基线”？为什么不直接读当前工作树？

**回答主干：** 构建开始时选定一个 Git 提交，在独立快照中读取 blob、路径和源码范围，所有实体、关系和中文说明都能回到同一版本复查。当前工作树可能在 Agent 操作中持续变化，如果直接把它当基线，同一个实体的来源会随编辑漂移，检索结果、审阅记录和审计结论就难以复现。活动修改仍可作为 overlay 被记录，但不会悄悄改写基线事实。

**继续追问：固定提交是不是意味着知识库永远过期？** 不是。新提交通过迁移流程进入 staging：只有路径、语言、blob 和旧解析状态完全匹配的文件才复用事实与审阅，其余文件重新解析和复核；新版本通过完整审计后再切换，旧输出保留到回滚探针通过。

### 62. “固定 Git 快照驱动”中的“驱动”具体驱动什么？

**回答主干：** 快照不是一个备注字段，而是构建和审计的共同输入。解析器从该快照读源码，语言服务器在该快照上提供语义证据，机器库保存来源，页面链接指向对应路径和范围，迁移按 blob 判定能否复用，最终审计再检查所有事实是否仍指向同一提交。这样“源码版本—机器事实—人类解释—检索结果”形成闭环。

### 63. 三层知识库是哪三层？为什么不能只保留 SQLite？

**回答主干：** 第一层是 `facts/`，保存可重建、来源绑定的权威中间事实；第二层是 `machine/knowledge.sqlite`，保存完整实体、关系、来源文本、中文章节和 FTS5 索引，服务 Agent 检索；第三层是 `human/` 中文导航及字节一致的 `markdown/` 兼容镜像，服务人类阅读。只留 SQLite 会丢失独立重建入口和可读导航；只留 Markdown 又会丢失完整关系、精确来源和高效检索。

**画图顺序：** 固定提交 → Tree-sitter/LSP → `facts/` → `machine/knowledge.sqlite` → 预算化 Agent pack；机器事实经受控投影得到 `human/` 与 `markdown/`。

### 64. Tree-sitter 和 LSP 分别解决什么问题？为什么需要融合？

**回答主干：** Tree-sitter 擅长稳定提取文件、类、函数、方法和语法范围，即使源码局部不完整也能提供结构；LSP 擅长给出定义、引用、诊断等依赖项目环境的语义证据。仅靠语法树难以准确判断跨文件引用，仅靠 LSP 又可能受项目配置、依赖或服务端行为影响。CKB 保留两类证据及其状态，由提供器适配层统一建模，而不是把其中一个伪装成另一个。

### 65. 如果 LSP 返回空结果或不可用，系统会怎样？

**回答主干：** 空 `documentSymbol` 可能是合法结果，例如只有导入或顶层调用的模块，因此不能把“空列表”直接当故障；协议失败、致命诊断和能力缺失才进入相应失败或近似状态。允许的近似模式必须记录精度边界和 fallback evidence，关键语义门未满足时不写完成标记。Tree-sitter 可以保留语法事实，但不能冒充已获得精确语义关系。

### 66. 为什么让确定性脚本决定实体归属，而不是让 Agent 选重要代码？

**回答主干：** 实体归属会影响页面数量、关系入口、上下文预算和多次运行的一致性。如果交给 Agent，每次选择可能不同，难以复现 benchmark，也难以判断页面变化来自源码还是模型偏好。脚本按固定规则把实体放入独立页面、附录或边界页；Agent 的优势用于解释精确来源，而不是改变结构规则。

### 67. “审计门”到底审计什么？

**回答主干：** 审计门不是一次格式检查，而是完成条件集合：来源范围可回溯、实体与关系完整、中文叙述合规、页面链接有效、`human/` 与 `markdown/` 镜像一致、工作记录可发现、两个 SQLite 索引完整、开放反馈可解析、项目级 Agent 协议有效，以及总完成、机器完成和人类完成三个标记一致。任一关键门失败时保留 pending 或 failed 状态。

### 68. Agent 只做来源复核，会不会没有充分发挥大模型能力？

**回答主干：** 这是有意的职责切分。结构选择、配额、排序和验收需要可重复，交给脚本；源码职责、修改时机和自然语言关系需要语义理解，交给 Agent，但限制在精确路径和范围内。这样模型仍承担最需要理解的工作，同时输出能被来源和审计复核。项目重点不是追求 Agent 自主程度最大，而是把不确定性放在可审阅的位置。

### 69. SQLite FTS5 是什么？为什么没有直接使用向量数据库？

**回答主干：** FTS5 是 SQLite 内置的全文检索模块，可在标识符、路径、中文职责、章节和来源文本上建立倒排索引。它本地、事务一致、可离线重建，排序输入和版本容易固定。当前检索还没有证据证明引入 embedding 能在下游任务质量上抵消模型版本、索引重建、资源和不可重复性成本，因此先使用 FTS5 加确定性图传播；向量检索要在独立 benchmark 证明收益后再进入正式链路。

### 70. 为什么 FTS5 后面还需要图检索？

**回答主干：** FTS5 擅长找到与查询词直接相关的种子，但真实修改入口可能是被调用函数、测试、配置入口或邻接职责，文本未必重复同一关键词。图传播从高分种子沿来源中已有的调用、引用、测试和邻接关系扩展候选，使结果既有词法相关性，也保留代码结构上的协作关系。最后仍受候选上限和 token 预算约束。

### 71. “固定权重图传播”中的权重由谁确定？怎样保证结果稳定？

**回答主干：** 权重由版本化代码中的关系类型规则确定，并结合度数惩罚、固定候选窗口和稳定 tie-breaker 排序；同一快照、数据库、查询、配置和版本应返回相同结果。`fast` 使用受限跳数的传播，`precise` 使用固定迭代的加权 PageRank。权重不是 Agent 在查询时生成的，因此可以通过重复查询、结果签名和冻结回归集审计。

### 72. 图里的边可靠吗？会不会把模型推断当成源码事实？

**回答主干：** 关系必须保留提供器证据和来源状态，机器层区分提取、推断和歧义关系；人类页面只呈现经过聚合、受配额限制的自然语言导航，不删除机器侧证据。图传播使用这些已入库关系，Agent 不能凭叙述临时新增高权重边。面试时应承认：语法或语言服务器关系仍可能不完整，因此关键修改前要通过 `source` 或窄范围源码读取复核。

### 73. 什么叫“生成 token 预算内源码入口”？预算怎样生效？

**回答主干：** 检索不会把所有命中页面和完整源码都塞给 Agent，而是先排序候选，再按固定 token 估算和章节优先级选择内容，输出页面职责、相关关系、源码路径、范围和可继续下钻的命令。预算耗尽后停止扩展，Agent 如需精确实现再调用 `entity`、`neighbors` 或 `source`。因此减少的是首轮检索占用的上下文，不是压缩源码本身。

### 74. Recall@8 的 100% 是怎样计算的？

**回答主干：** 每个问题事先有目标文件集合，检查方法返回的前八个文件是否覆盖目标文件，再对全部问题汇总。本轮 Flask 3.1.3 的十个修改意图问题中，常驻 CKB 和 `git grep` 都命中 10/10 个目标文件，所以目标文件 Recall@8 都是 100%。这个指标衡量首轮文件导航，不衡量函数级精度、答案正确率或修改是否通过测试。

### 75. 为什么基线写“基于预设关键词的 git grep”，而不是“人工 git grep”？

**回答主干：** “人工 git grep”容易被理解为人工浏览、临场调词或手工判断结果。实际基线是每题预先设计四组关键词，并固定命令、覆盖数、命中行数和路径排序，最多展示八个文件；正式运行时脚本按协议执行。写“基于预设关键词的 `git grep` 基线”既承认关键词含有工程师先验，又明确测量过程是确定性的。

### 76. “检索占用的上下文从 11,228 降至 2,294 tokens”具体统计了什么？

**回答主干：** 统计的是检索阶段向 Agent 展示的结果文本，而不是整个任务的系统提示、对话历史、源码修改和测试输出。每个问题先计算可见检索输出的 token 数，再比较十个问题的中位数；`git grep` 为 11,228 tokens，CKB 阅读包为 2,294 tokens，按 `(11,228-2,294)/11,228` 约为 79.6%。简历为了压缩篇幅写“检索占用的上下文”，面试展开时要补充“这里比较的是中位数”。

### 77. 后两个指标怎样证明是在与 git grep 对比？

**回答主干：** 两个指标都使用同一轮 Flask 3.1.3 对照记录：上下文是 CKB 2,294 对 `git grep` 11,228 tokens；P95 是 CKB 47.6 对 `git grep` 86.3 ms。简历先写“相比 `git grep`”，再并列给出两个端点，语法上共同受该比较关系约束。面试口述可直接说：“相对预设关键词的 `git grep` 基线，上下文中位数减少 79.6%，P95 从 86.3 降到 47.6 毫秒。”

### 78. 为什么常驻 CKB 的 P95 会低于 git grep？这是不是不公平？

**回答主干：** 本轮比较的是实际 Agent 会话中的完整调用路径：CKB 复用已启动的 Python 进程、SQLite 连接和静态检索缓存，`git grep` 基线按题执行固定命令。结果说明“预构建索引加常驻服务”的系统方案在该协议下尾延迟更低，不等价于证明 FTS5 算法本身一定比 grep 快。输入也不完全对称：CKB 接收中文自然语言任务，grep 使用预设关键词；因此应把它称为实用工作流对照，并公开构建成本和输入差异。

### 79. P95 从 86.3 ms 降到 47.6 ms 意味着什么？为什么不只报平均值？

**回答主干：** P95 关注尾部体验：大约 95% 的正式请求延迟不超过该分位附近，能暴露偶发慢查询；中位数反映典型请求，两者结合比平均值更不容易被少量极端值误导。同轮数据中，中位数是 73.2 ms 降至 24.9 ms，P95 是 86.3 ms 降至 47.6 ms。简历选择 P95，是为了强调交互式 Agent 会话的稳定等待时间，而不是隐藏中位数。

### 80. 两种方法文件 Recall@8 都是 100%，CKB 的价值在哪里？

**回答主干：** 文件召回相同说明 CKB 没有用更小上下文换取文件级漏检。它的增量价值是把文件职责、相邻关系、源码范围和二次下钻入口组织在 2,294-token 的阅读包中，并在常驻路径降低尾延迟。另一方面，grep 对已知符号仍然更强，所以项目的价值不是“击败搜索命令”，而是把未知仓库的自然语言意图先转成受控源码入口。

### 81. 为什么精确目标符号召回只有 40%，还敢把 Recall@8 100% 写进简历？

**回答主干：** 两者回答不同问题。目标文件 Recall@8 衡量首轮能否找对修改文件，精确目标符号召回衡量结果是否直接包含预标注函数；本轮 CKB 是 40%，`git grep` 是 100%。简历明确写“目标文件 Recall@8”，没有把文件指标冒充符号指标。面试时应主动说明这一短板，并给出“CKB 定位文件与职责，精确符号查询或窄范围 grep 落到函数”的组合流程。

### 82. 构建知识库要付出多少成本？延迟数字是否把它排除了？

**回答主干：** Flask 知识库成功构建、逐实体复核、合并和最终审计约用 92.1 秒，其中机器构建、合并与最终审计约 20.1 秒，逐实体来源复核与审阅提交约 72.0 秒。47.6 ms 和 86.3 ms 比较的是查询阶段，不包含这项一次性成本。是否值得构建取决于仓库复用次数、任务类型和迁移复用率；一次精确符号查询通常直接用 grep 更合适。

### 83. 这组 Flask 数据能否推广到大型仓库或其他语言？

**回答主干：** 不能直接推广。当前证据范围是 Flask 3.1.3 的 24 个核心 Python 文件、十个固定修改意图和本机同轮运行。多语言架构能力来自 Tree-sitter 与不同 LSP 提供器的实现和审计，性能收益仍需在其他语言、仓库规模和任务分布上独立复验。面试中可以说“在 Flask 3.1.3 实验中确认”，不能说“所有仓库平均减少 79.6%”。

### 84. 这个项目里哪些是你的工作，哪些是第三方能力？

**回答主干：** Tree-sitter 提供语法解析基础，Pyright 等语言服务器提供语义能力，SQLite 提供事务、FTS5 和完整性检查，Graphify 提供关系管线思想。个人工作应表述为：设计固定 Git 来源与三层架构，完成多语言提供器适配和统一事实模型，实现确定性实体归属、FTS5 与固定权重图检索、token 预算和常驻协议，并建立来源复核、审计、迁移、自动化与回滚链路。不要表述为从零实现了解析器、语言服务器、数据库或上游关系框架。

### 85. 如果继续做一轮，最优先改什么？

**回答主干：** 优先增加“文件命中后按限定名、函数签名和局部调用关系进行二次确定性重排”，保持首轮上下文预算不变，并用同一协议复验精确目标符号召回。随后再用固定模型执行真实修改、测试和回滚任务，比较任务成功率、误改文件、二次检索次数、总 tokens 和墙钟时间；只有下游效果门通过，才把组件指标升级为 Agent 任务收益。

### 三十秒回答模板

我做的是面向代码 Agent 的多语言代码知识基础设施。它以固定 Git 提交作为可追溯事实版本，用 Tree-sitter 和语言服务器构建可重建事实、完整机器检索库和中文导航三层架构；结构选择和审计由确定性脚本负责，Agent 只复核精确源码范围。查询先用 SQLite FTS5 找种子，再按固定权重沿代码关系扩展，并在 token 预算内返回源码入口。在 Flask 3.1.3 的同轮实验中，它与预设关键词 `git grep` 的目标文件 Recall@8 都是 100%，但检索上下文中位数少 79.6%，P95 从 86.3 降到 47.6 毫秒；精确符号召回仍只有 40%，所以工程上采用“CKB 先找文件和职责，符号查询再落函数”的组合方案。

### 三分钟展开顺序

1. **问题：** 陌生仓库任务中，直接搜索常返回大量词法命中，Agent 既难判断职责，也浪费上下文。
2. **架构：** 固定 Git 提交绑定来源；Tree-sitter 与 LSP 形成事实；`facts/`、机器 SQLite 和中文导航分层保存。
3. **可控性：** 脚本固定实体归属、排序、图权重、预算和审计；Agent 在精确范围内复核语义叙述。
4. **检索：** FTS5 找直接候选，固定权重图传播补充调用、引用、测试与相邻职责，最终输出预算化源码入口。
5. **证据：** 说明 Flask 范围、预设关键词基线、70+70 条记录、文件 Recall@8、上下文和 P95。
6. **边界：** 主动说明输入不对称、构建成本未计入查询、符号召回 40%、结果不外推全部仓库。
7. **下一步：** 做文件内确定性符号重排，再用端到端修改 benchmark 验证真实任务收益。

## 基础概念速查补充：当前简历新增口径（2026-08-30）

原“基础概念速查”已经准确解释 AST/Tree-sitter、LSP、commit/blob/range、知识图谱、SQLite FTS5、PageRank、token 预算、Recall@8 和 P50/P95。本节只补充当前简历中新增、但尚未作为独立基础概念展开的九个口径，避免重复已有定义。

### 固定 Git 提交与快照驱动

“固定 Git 提交”表示构建开始时选择一个确定提交，并在独立快照中读取文件 blob、路径和源码范围；解析、语言服务器证据、机器事实、人类说明和检索结果都回到同一源码版本。“快照驱动”进一步表示这个版本不是备注，而是构建、来源审阅、审计、迁移和回滚共同使用的输入。活动工作树可以继续修改，但只作为独立 overlay 记录，不会悄悄改写基线事实。

### 三层知识架构

- **事实层 `facts/`**：保存来源绑定、可重新构建的权威中间事实。
- **机器检索层 `machine/knowledge.sqlite`**：完整保存实体、关系、来源、中文章节、FTS5 索引和图检索所需数据，服务 Agent。
- **中文导航层 `human/` 与 `markdown/`**：把机器事实投影成数量受控、可阅读、可回到源码的人类页面。

三层不是三份相同副本：事实层保证可重建，机器层保证完整检索，人类层降低阅读负担。机器层可以比人类层包含更多实体、关系和来源属性。

### 确定性结构决策

确定性脚本根据版本化规则决定实体进入独立页面、附录还是边界页，并固定候选窗口、排序、关系配额、上下文预算、稳定 tie-breaker 和完成门。同一快照、数据库、查询、配置和版本应得到相同结构与结果。这样可以区分“源码真的变化”与“模型临时偏好变化”，也使 benchmark 和回归检查可复现。

### Agent 来源复核

Agent 来源复核是指：脚本先给出精确路径和源码范围，Agent 再检查中文职责、修改时机和关系叙述是否能由这些来源支持。Agent 不决定实体重要性，不修改事实 ID、图权重、页面配额或审计结论。该分工不是削弱 Agent，而是把模型不确定性限制在可以逐条复查的叙述层。

### 审计门的层次

审计门是根据当前文件和数据库重新计算的验收规则，不是一次成功日志。CKB 的完成条件至少包括：来源范围可回溯、实体和关系完整、中文叙述合规、页面链接有效、Human/Markdown 镜像一致、工作记录可发现、两个 SQLite 索引完整、开放反馈可解析、项目级 Agent 协议有效，以及总完成、机器完成和人类完成三个标记一致。任何关键门失败时都不把输出描述为完成。

### 常驻 CKB

常驻 CKB 指在一个 Agent 会话内复用已启动的本地 Python 进程、SQLite 连接和静态检索缓存，通过 JSONL stdio 接收请求。它不监听网络端口，也不改变 FTS5、图传播、token 预算和来源链接的排序合同。常驻指标反映进程已经驻留后的会话路径，必须与冷 CLI、首次请求和缓存未命中分开报告。

### token 预算内源码入口

“源码入口”不是只返回文件名，也不是直接生成修改答案，而是返回任务相关的职责、相邻关系、源码路径、精确范围和继续下钻命令。检索先对候选排序，再按固定 token 估算选择页面和章节；需要实现细节时再使用 `entity`、`neighbors` 或 `source`。因此预算控制首轮阅读包的大小，底层事实仍保持完整。

### 检索占用的上下文

“检索占用的上下文”只统计检索阶段向 Agent 展示的结果文本，包括返回的职责、关系、路径、范围或 grep 输出；它不等于系统提示、对话历史、后续源码读取、修改、测试和回滚构成的任务总上下文。当前简历中的 11,228 与 2,294 tokens 是各题检索输出的中位数，79.6% 是两种检索路径的相对减少比例。

### 基于预设关键词的 git grep 基线

该基线在正式运行前为每个问题准备固定关键词组，并固定 `git grep` 命令、关键词覆盖数、命中行数、路径排序和最多八个返回文件；执行阶段由脚本完成，不进行临场调词或人工浏览。它含有工程师的关键词先验，因此与接收中文自然语言的 CKB 是实用工作流对照，不是完全相同输入下的纯算法对照。
