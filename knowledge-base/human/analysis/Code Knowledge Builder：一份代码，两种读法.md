# Code Knowledge Builder：一份代码，两种读法

标签：#类型/分析

## 前言：一份代码，两种读法

每个代码库都已经保存了大量知识。类和函数说明系统能做什么，测试说明哪些行为必须保持，提交记录留下变化发生的时间，设计文档则保存了一部分选择理由。问题通常不是知识完全缺席，而是这些知识分散在不同文件、不同工具和不同时间里，只有熟悉项目的人知道怎样把它们重新拼起来。

对刚接手项目的人来说，这种分散首先表现为阅读困难。目录能够显示文件放在哪里，却很少说明应该从哪里开始；搜索能够找到名称，却不会直接指出哪个结果负责当前行为；调用关系能够列出连接，却还需要人判断哪些连接会影响修改，哪些测试能够证明修改成立。

对 Agent 来说，困难有另一种形状。它可以在很短时间内打开大量文件，但上下文窗口有限，文件数量也不等同于正确的任务入口。如果来源版本、符号范围、关系和验证路径没有提前组织好，Agent 得到的往往是很多相关内容，而不是足以形成修改计划的那部分内容。

Code Knowledge Builder 同时从这两种困难出发。

机器知识库保存完整的文件、实体、源码范围、关系、诊断、审阅和工作记录，使 Agent 可以按问题检索，并在需要时回到精确来源。人类知识库则主动缩小可见内容，把同一批事实重新组织成少量简体中文页面：这一页负责什么，什么任务应该从这里开始，相关代码为什么值得继续查看，修改后应该进入哪个测试。

这两层有意采用不同的表达方式。机器层追求完整和可查询，人类层追求清楚和可行动；机器层保留内部标识、来源证据和完整关系，人类层使用自然标题、职责说明和阅读链接。人类页面的克制没有减少底层事实，机器数据的完整也不会把实体清单直接推给读者。

真正把两层连接起来的是同一条来源链。页面选择、实体归属、关系预算和检索排序由确定性脚本控制，Agent 在固定源码范围内补充中文解释，最终审计再分别检查机器知识、人类页面和两者之间的映射。于是，人看到的说明和 Agent 取回的上下文虽然形状不同，指向的仍是同一份代码事实。

这也是理解 Code Knowledge Builder 的最佳入口：它不是一个单独给 Agent 准备的搜索索引，也不是一个批量生成 Markdown 的文档工具。它建立的是一套共同的代码知识基础——机器能够精确查找，人能够自然阅读，双方都能沿着来源、修改和验证继续工作。

本文沿着这条主线展开。第一部分讨论代码已经存在时，为什么还需要单独构建知识；第二部分说明知识可信所依赖的 Git 来源、语法事实和语义证据；第三部分进入事实、机器和人类三层；第四部分解释脚本、Agent 和审计如何分工；第五部分分别走完人类和 Agent 的使用路径；第六部分说明分析、修改、会话和反馈如何持续积累；最后一部分讨论验证、边界和项目背后的工程原则。

如果只想快速理解项目，可以依次阅读第 2、7、10、13 和 17 章。它们分别回答双读者设计、三层知识、完成状态、真实任务闭环和总体设计原则。准备实现或维护时，则适合从头顺序阅读，因为后面的命令、数据结构和审计边界都建立在前面的来源合同之上。

## 第一部分：为什么还需要代码知识库

### 第 1 章：代码在那里，知识在哪里

代码库最容易给人一种错觉：只要源码还在，知识就没有丢失。严格地说，这句话成立。函数体、测试断言、配置和提交对象确实保留了大量事实。但“事实仍然存在”和“读者能够在当前任务中使用这些事实”是两件不同的事。

一个修改请求通常不会按照目录结构提出。用户会说“让精确符号排在同名文档前面”“C# 项目没有 restore 时也要得到稳定诊断”“Stop 事件应该形成待审阅记录”。这些表达描述的是行为、约束和结果，而源码按照模块、类和函数组织。读者首先需要把任务语言翻译成代码入口，然后再确认调用路径、数据边界和验证场景。

传统搜索解决其中最表层的问题。`grep` 可以迅速列出一个词出现在哪里，IDE 可以跳到定义和引用，语言服务器可以给出符号和诊断。它们都很重要，却分别只回答局部问题：字符串搜索缺少职责关系，符号跳转依赖已知名称，语言服务器了解程序结构，却不了解当前团队为什么把某个模块视为核心入口。

人类熟悉项目以后，会在脑中形成一张隐式地图。他知道 `ckb.py` 只是命令路由，真正的检索排序在 `machine_knowledge.py`；知道页面生成与机器实体构建属于不同阶段；知道一个测试通过只证明某一层行为，而不是整个交付已经成立。这张地图很少完整写在单个文件里，却决定了修改速度和质量。

Agent 缺少的正是这张隐式地图。它可以临时重建，但每次会话重新扫描、重新判断、重新选择入口，会反复消耗上下文和时间。更麻烦的是，不同 Agent 对“哪些文件重要”“关系应该扩展多深”“多少内容足够”可能给出不同答案。即使最终都能完成任务，过程也难以复现和审计。

因此，Code Knowledge Builder 处理的不是源码保存问题，而是源码事实的可使用性问题。它需要把分散在代码、测试、Git、语言工具和工作记录中的信息组织起来，让读者回答四个问题：

1. 当前任务应该从哪里进入；
2. 这个入口为什么与任务有关；
3. 修改会影响哪些相邻行为；
4. 哪个测试或命令能够观察结果。

对于人类，这四个问题决定知识页面是否可行动。对于 Agent，它们决定检索结果是否足以形成修改计划。两类读者在这里遇到了同一个问题，只是需要的答案形状不同。

### 第 2 章：人和 Agent 需要的不是同一张页面

如果把机器知识库直接展示给人，会得到一份非常完整、也非常沉重的实体清单。几百个声明、上千条关系、内部 ID、来源对象、分类字段、诊断和审阅状态全部可见，真实性很强，阅读入口却被淹没。反过来，如果只保留几页经过高度概括的中文说明，读者可能感觉清楚，Agent 却会失去精确符号、完整关系和源码范围。

这不是排版问题，而是任务不同。

Agent 面对的是查询任务。它需要完整候选、确定性排序、精确来源和严格预算。一个当前没有进入人类页面的局部辅助函数，仍可能成为故障定位的关键证据；一条不适合在人类页面展示的低层关系，也可能在路径查询中连接两个模块。机器层删掉这些内容，会直接伤害召回。

人类面对的是理解和行动任务。读者需要先知道某一页产生什么结果、什么情况下应该从这里开始，以及下一步最可能查看哪个修改或验证入口。页面如果先展示二十个字段和四十条关系，事实虽然完整，首屏任务却没有完成。

Code Knowledge Builder 因此采用双层知识库，而不是把同一份页面换成两种格式：

| 维度 | 机器知识库 | 人类知识库 |
|---|---|---|
| 目标 | 完整、可查询、来源可复核 | 可发现、可理解、可行动、可信任 |
| 内容 | 全部实体、关系、源码、诊断、审阅和工作记录 | 受控数量的类、函数、职责聚合和工作记录 |
| 关系 | 完整机器关系与证据 | 说明点击目的的自然阅读链接 |
| 语言 | 结构化字段与源码标识符 | 简体中文叙述，保留必要标识符 |
| 读取方式 | SQLite 精确查询、FTS、图传播和预算包 | 首页、职责导览、工作记录、搜索和双链 |
| 完成证据 | 完整性、来源、索引、确定性和预算 | 中文、导航、链接、首屏职责和任务可达性 |

双层设计的关键不在于复制，而在于投影。事实层提供共同基础，机器层完整保存，人类层按照确定性规则选择和重新表达。人类页面中的一句职责说明必须能够回到机器实体和源码范围；机器层中的某个实体是否拥有独立人类页面，则由页面配额和归属规则决定。

这使人类友好成为一条独立设计主线。它不依附于 Agent 检索，也不由“Markdown 能打开”自动成立。一个人类页面需要让读者找到入口、理解职责、形成行动并判断可信度。机器检索同样是一条独立主线，需要召回、符号、上下文和延迟指标。两条主线共享来源，分别验收。

## 第二部分：先建立可信的事实基础

### 第 3 章：固定 Git 来源

知识库中的一句说明如果只写“这个函数负责检索”，读者还会追问：基于哪个版本？函数在什么文件和范围？当前工作树已经修改过，它描述的是修改前还是修改后？Code Knowledge Builder 先解决这些问题，再讨论页面和搜索。

构建从一个干净的 Git commit 开始。commit 固定项目状态，blob 固定单个文件内容，精确 range 固定声明在文件中的位置。三者共同构成来源证据：commit 说明整体版本，blob 证明文件字节，range 把知识断言落到具体代码。

语义分析运行在 detached snapshot 上，而不是持续变化的活动工作树上。这样，Tree-sitter、语言服务器、实体关系和 Agent 审阅面对的是同一份输入。构建需要数分钟甚至更长时，用户仍然可以在 live worktree 继续工作；这些变化进入独立 overlay、会话或变更记录，不会悄悄改变基线知识。

这种分离解决了一个常见矛盾：长期知识需要稳定，开发工作需要继续。冻结整个项目直到知识库完成会妨碍正常开发，直接扫描活动工作树又会让不同批次看到不同状态。detached snapshot 提供稳定语义根，overlay 记录正在发生的变化，两者各自承担一种时间尺度。

对于还没有 Git commit 的目录，系统不会自动替用户创建历史。只有用户明确选择 `--init-git`，构建器才初始化仓库、暂存当前状态并创建一次初始提交。已有 Git 仓库即使传入该参数也不会被重复提交；已有脏工作树则继续触发前置失败，避免把未确认变化混进固定来源。

局部知识库也沿用同一合同。`--scope-path` 可以限制到文件或目录，`--entry LANGUAGE:PATH#QUALIFIED_NAME` 可以从类或函数开始并按深度扩展。局部构建仍会记录一跳边界，使读者知道所选范围与外部代码在哪里连接。但它的完成状态只覆盖所选范围和记录边界，不扩张为整个仓库已经完成。

当源码进入新 commit，迁移会比较 blob 和实体来源。未变化的精确 blob 可以复用，变化范围需要重新解析和审阅，持续积累的分析、修改、实验和会话记录则按独立规则保留。迁移的目标不是让所有旧结论自动延续，而是明确哪些事实仍然有同一来源，哪些说明需要重建。

固定 Git 来源增加了前置条件，也换来了知识可追溯、构建可恢复和结果可比较。后面的每一层——机器检索、人类页面、Agent 解释、Benchmark 和完成标记——都依赖这条稳定来源链。

### 第 4 章：从语法事实到语义证据

Git 固定了输入，却还没有解释代码。下一步是把文件内容转成实体、范围、关系和诊断。Code Knowledge Builder 将这项工作拆成语法提取、语义提供和来源审阅，而不是把全部理解交给单一工具。

Tree-sitter 首先建立语法结构。它能够识别类、函数、方法、字段、调用形状和声明范围，为多语言提供统一的基础实体。语法树适合回答“这里声明了什么”“范围从哪里到哪里”“哪些节点在结构上相邻”。这些事实稳定、速度快，也便于分批处理。

语言服务器补充语义证据。Python 使用 Pyright，标准 JavaScript 使用 TypeScript Language Server，C/C++ 使用 clangd，C# 使用 csharp-ls 与 .NET 工程上下文。它们提供定义、引用、诊断和项目级解析信息，帮助构建器区分同名符号、跨文件调用和只靠语法难以确认的关系。

共享管线并不意味着所有语言具有相同条件。C/C++ 是否存在 compilation database 会影响 clangd 的完整性；C# 需要选择唯一的 solution 或 project，多候选时应返回候选让用户决定；没有项目时可以使用隔离、无 restore 的 fallback 项目，并明确标记为 `bounded-approximate`。依赖 restore 只有在用户显式选择 `--allow-dotnet-restore` 时才会发生。

构建核心遵循 `detect → extract → build → cluster → report/export` 的总体顺序：

1. `detect` 确定语言、项目结构和可用提供器；
2. `extract` 从语法树和语义工具收集声明、范围与关系；
3. `build` 形成来源绑定的实体图和证据；
4. `cluster` 按确定性图规则形成职责群；
5. `report/export` 生成机器知识、审阅包和人类投影候选。

语法和语义工具只提供事实证据，不直接决定人类页面应该怎样写。语言服务器知道一个函数引用了什么，却不知道读者什么时候应该从这个函数开始；图算法可以形成连接紧密的群组，却不适合独立生成可靠的中文职责。后者进入 Agent 审阅阶段。

解析成功也不是整个语言能力的完成证明。命令行参数存在、模块通过 `py_compile`、Tree-sitter 能够产生节点，都只能证明对应层面。真正的语言支持还需要 provider 路由、项目选择、诊断、实体范围、关系、测试、投影和完成门共同成立。

这一章的结果是一套可重建事实，而不是最终文档。接下来要回答的问题是：这些事实怎样分别进入机器知识库和人类知识库，又怎样保持同一来源？

## 第三部分：同一事实如何服务两类读者

### 第 5 章：机器知识库为什么追求完整

`machine/knowledge.sqlite` 是 Agent 面向项目提问时的主要入口。它保存全部文件、实体、源码范围、关系、提供器证据、诊断、审阅、职责群、边界、人类归属、固定源码、工作记录和可选参考资料。一个实体是否进入人类页面，不影响它在机器层中的存在。

完整保存的直接价值是检索时保留选择余地。今天没有被认为重要的局部函数，明天可能成为故障根因；一条低权重调用关系，可能在跨模块路径查询中连接两个关键组件。机器层过早删除信息，会把构建阶段的判断变成不可恢复损失。

完整并不意味着每次全部加载。数据库同时建立分节全文索引、实体索引、源码索引和关系图。Agent 的问题先命中有限候选，再按固定权重扩展关系，最终渲染到 token 预算内的阅读包。完整性属于存储合同，有界性属于读取合同，两者没有冲突。

说明字段也按章节拆分。一个实体的中文含义、职责、修改时机、来源核对和源码片段分别进入可查询 section；工作记录按照 Markdown 标题拆节。检索可以命中“什么时候需要修改”而不加载整个页面，也可以只取某项实验的结论和边界。

默认检索保持纯确定性。`fast` 使用精确锚点、分节 FTS 和有界图传播；`precise` 增加源码 FTS 与固定轮次的加权排序。词法、权重、惩罚、同分顺序和预算规则都固定，重复查询因此可以比较结果签名。向量模型只有在冻结 Benchmark 证明收益、成本和失败边界后才适合进入正式路径。

机器层还保存持续工作。analysis、change、experiment、pitfall 和 session 作为文档进入 sections；Hook 产生的待审阅记录也可以被检索，但原始或近原始会话证据保持在机器侧。这样，Agent 查询“为什么改过这个模块”时，既能看到固定代码事实，也能找到后续决策和实验。

SQLite 在这里承担的不只是存储。它提供事务、FTS5、批量 SQL、完整性检查和单文件交付；常驻 stdio 模式还可以复用连接、索引和静态缓存，减少每次启动成本。数据库能够通过 `PRAGMA integrity_check` 独立验证，索引数量和文档数量也能与投影清单重新对照。

机器知识库的理想状态不是“看起来智能”，而是完整、稳定、可查询、可复核。它为 Agent 提供选择空间，同时把每次实际读取限制在任务需要的范围。

### 第 6 章：人类知识库为什么主动克制

人类层从相反方向出发。它首先考虑读者完成任务需要多少页面、多少跳转和多少判断，而不是数据库里一共有多少实体。

默认情况下，普通文件只选择少量关键实体；核心文件和邻近文件使用受控配额；访问器、简单判断、局部辅助函数、薄包装、枚举和字段进入一句中文附录。附录仍然可以追溯到机器实体，但不会让每个实现细节都占据独立页面。

这种克制保护了信息层级。如果 `INDEX.md` 直接列出几百个符号，读者仍然要先判断哪个符号与任务有关。职责导览先按模块和结果组织入口，类与函数页再说明职责、修改时机和源码位置，内部细节最后展开。阅读顺序与任务判断顺序保持一致。

一个稳定代码页的首屏应该回答三个问题：

1. 这一页负责产生什么结果；
2. 什么任务应该从这里开始；
3. 下一步最可能查看哪个修改或验证入口。

后续内容再展开关键流程、来源位置、上游输入、核心依赖、下游调用、修改联动、测试覆盖和内部细节。关系链接需要说明点击目的，例如“修改排序权重时同时查看候选合并逻辑”，而不是只写“会使用这里的行为”。

简体中文在这里是完成条件。类名、函数名、API、命令和路径保留源码形式，职责、关系、修改时机、来源说明和工作记录则使用中文。这样既保持精确标识，又让页面脱离源码上下文后仍然能够独立阅读。

人类友好由四个维度共同决定：

- **可发现**：知道从首页、职责导览、工作记录还是精确检索进入；
- **可理解**：看懂职责、进入条件、流程和约束；
- **可行动**：能够到达源码、影响关系和测试；
- **可信任**：能够追溯固定范围、审阅状态和完成门。

页面整洁只覆盖其中一部分。所有页面从首页可达也只证明导航没有断裂；真正的任务可读性还需要固定问题集，测量读者是否命中目标页面、是否找到验证入口、经历多少跳转、是否发生错误回退。

Human 目录可以直接作为 Obsidian vault 打开，`markdown` 提供兼容镜像；Logseq 使用输出根的文件图谱配置。编辑器状态和用户自有文件由生成器清单隔离，重新投影不会把知识维护变成工作区重置。

### 第 7 章：事实层、机器层与人类层

双层知识库之下还有事实层。三层的分工可以概括为：事实层负责重建，机器层负责查询，人类层负责理解与行动。

| 层 | 主要内容 | 主要读者 | 主要完成门 |
|---|---|---|---|
| facts | 文件、实体、范围、关系、来源清单、审阅清单和计数合同 | 构建器与审计 | 来源完整、实体集合一致、关系端点有效 |
| machine | SQLite 中的完整事实、源码、章节、诊断、审阅、工作记录与检索索引 | Agent 与工具 | SQLite 完整、索引一致、检索确定、预算有效 |
| human | 中文代码页、职责导览、工作记录、反馈和编辑器导航 | 人类读者 | 中文、链接、镜像、可达性、页面合同和可读性 |

facts 是可重建依据，通常不直接承担日常阅读。machine 从 facts 和 Agent 审阅构建完整查询层。human 再根据固定页面配置和审阅文字形成保守投影。任何一层的压缩都不会反向删除上层事实。

三层分别完成，也必须一起一致。机器实体完整不代表人类页面已经可读；Human 页面自然不代表机器索引包含全部范围；facts 能重建不代表当前 SQLite 没有损坏。项目因此保留总完成、机器完成和人类完成三个标记，`finalize` 只有在全部门通过后才写入。

`human` 与 `markdown` 是字节兼容镜像，但用户状态可以按合同排除。稳定生成页面由清单管理，分析、变更、实验、踩坑、会话、反馈和 Obsidian 工作区则按各自所有权保留。生成器清楚知道哪些文件可以替换，哪些内容属于长期人工知识。

外部参考资料也与固定源码事实分开。参考文章、论文或其他项目可以进入受控 reference 记录，拥有状态、页面配额和机器索引，却不会因为被引用就变成源码实体。动态会话记忆同样可以补充工作上下文，并且与 commit、blob 和 range 证据分属不同层次。

三层设计最终解决的是一份事实的多种用途。Agent 可以从机器层精确检索，人类可以从 Human 层理解和行动，审计可以回到 facts 重新计算。它们不是三份互相竞争的知识库，而是同一来源合同的三个职责层。

## 第四部分：知识是怎样生成的

### 第 8 章：确定性脚本负责选择

代码知识构建中最容易波动的部分，往往不是解析，而是“哪些内容重要”。如果每次都让 Agent 自由决定页面数量、核心实体、关系扩展和上下文长度，同一仓库在不同会话里可能得到不同结构。解释质量很难比较，失败也难以定位到底来自事实还是选择。

Code Knowledge Builder 把能够确定的判断交给脚本：

- 文件和实体分类；
- 页面所有权和附属实体归属；
- 核心、普通和邻近页面配额；
- 关系排序和每组预算；
- Agent pack 的实体集合和 token 预算；
- fast/precise 的词法、权重、传播轮次和同分顺序；
- 审阅字段、完成门和失败状态。

这些规则写入 `page-config.json` 和构建状态，并在初始构建后固定。页面数量、关系上限、可见章节、附录方式、上下文预算和审阅包预算都属于构建合同。构建中途为了通过审计而修改阈值，会破坏结果可比较性，因此需要新配置和新的构建边界。

Graphify 也运行在这一确定性边界内。完整关系图经过固定权重和聚类形成职责群，路径查询返回可复核的连接，人类关系报告使用中文描述结果。图算法负责给出结构，Agent 负责说明结构在源码中的含义。

确定性没有消除所有不确定性。词法规则可能漏掉隐含同义词，固定权重可能低估某个局部符号，职责群也可能和维护者的心理模型不同。但这些误差可以用冻结问题集复验，也可以精确定位到规则、权重或输入事实。相比一次性的自由判断，它们更容易修改和回归。

脚本的作用因此不是替代 Agent，而是界定 Agent 的任务。它把“解释哪些对象”固定下来，让 Agent 把上下文用于阅读源码和写清职责，而不是重新规划整个知识库。

### 第 9 章：Agent 负责解释

确定性脚本能够选择实体，却难以仅靠规则写出可靠的人类说明。函数名可能模糊，调用关系也不会自动表达设计意图。Code Knowledge Builder 在这里引入 Agent，但把它限制在来源绑定的解释任务中。

每个 review pack 固定待审阅实体、精确源码范围、相邻证据和需要填写的字段。Agent 重新打开这些范围，为主要实体写中文含义、职责、修改时机和来源核对，为附属实体写一句中文作用。它不重新决定页面数量，也不把范围外的推测写成事实。

这种审阅方式把 Agent 的长处用于语言理解。它可以结合函数体、类型、调用者和测试解释“这段代码为什么存在”，也能把多个低层实现整理成人类能够理解的职责。但每一句说明仍然拥有可追溯范围，审计可以检查中文、字段、链接和来源是否完整。

审阅包与解析批次独立。解析成功后可以生成多个 pack，某个 pack 失败只返工对应集合；提交审阅后，构建器再验证实体覆盖、范围、中文和格式。大型仓库因此不需要在一次上下文中完成全部解释。

分析、修改、踩坑和实验使用同一原则。Agent 先运行 `brief` 获取阅读包，再把结论通过 `record` 写入，并用 `--from-pack` 或现有页面链接绑定来源。工作记录可以包含判断和权衡，但必须区分已确认事实、由事实推导的结论和仍需核验的内容。

Agent 解释也有边界。源码往往只能说明当前实现，未必能证明创始人的原始意图；测试覆盖某个行为，也未必代表所有生产场景。可靠说明应当收窄结论，而不是用流畅语言填补证据空白。

项目把不确定性保留在最适合它的位置：集合、顺序和预算由脚本固定，含义和职责由 Agent 解释，最终状态由可重新计算的审计决定。

### 第 10 章：证据如何变成完成状态

一个命令返回成功，只能证明这一步没有以错误退出。Code Knowledge Builder 的完成状态来自多阶段证据，而不是单个命令或人工宣告。

完整构建通常经历初始化、分段解析、审阅包提交、跨段合并、人类投影和最终审计。`run` 可以串联常见路径并在审阅点停下；大型仓库或故障恢复则可以分别调用 `init`、`build-chunk`、`review-pack`、`merge` 和 `finalize`。

状态文件明确记录当前阶段：

- `.pending-agent-review` 表示事实已准备，但仍有 Agent 审阅任务；
- `.failed` 表示某项确定性门未通过；
- `.complete`、`.machine.complete` 和 `.human.complete` 只由 `finalize` 在全部门通过后写入。

全局审计至少检查来源、实体、关系端点、诊断、审阅覆盖、中文叙述、页面清单、双链、镜像、SQLite、Graphify、Logseq 配置和请求格式。人类可读性审计继续检查页面标题、标签、源码入口、导航可达性、关系信息气味和内部字段泄漏。

工作记录有独立维护门。Human 与 Markdown 页面需要一致，元数据标题唯一，`RECORDS.md` 必须覆盖全部记录，`agent-index.sqlite` 和 `machine/knowledge.sqlite` 都要能够检索目标。开放反馈、Agent Policy 和 reference 资料也进入 `maintain` 聚合检查。

因此，以下结果分别代表不同层次：

| 结果 | 能够说明什么 |
|---|---|
| 语法检查通过 | 文件可以被对应解释器解析 |
| 单元测试通过 | 测试覆盖的局部行为成立 |
| review pack 通过 | 指定实体完成来源绑定审阅 |
| machine audit 通过 | 机器事实、索引和来源合同一致 |
| human audit 通过 | 人类投影满足页面与镜像合同 |
| maintain 通过 | 工作记录、反馈、协议、参考资料和双层索引当前一致 |
| 三重完成标记存在 | 固定构建已经通过最终门 |

状态的价值在于让下一步明确。待审阅就继续审阅，某项审计失败就修复对应来源或投影，局部测试失败就回到目标行为。一个上游失败不会被重复包装成多个下游问题。

## 第五部分：人和 Agent 怎样使用它

### 第 11 章：人类如何找到、理解并修改代码

人类进入知识库时，第一步不是搜索所有页面，而是判断当前任务属于哪一种入口。

`INDEX.md` 提供四条路径：理解或修改代码进入职责导览；查找已有分析、变更和实验进入 `RECORDS.md`；精确定位符号交给机器检索；了解页面规则进入 `WIKI.md`。入口按任务组织，而不是按目录或数据结构组织。

假设读者想修改检索排序。他可以先从 `scripts` 职责导览找到机器检索区域，进入相关聚合页，阅读“它做什么”和“什么时候需要修改”，再沿相关代码查看候选生成、分节索引和图传播。页面中的测试链接应该说明具体覆盖的排序行为，而不是只给出测试文件名。

如果任务来自历史决策，`RECORDS.md` 更合适。它按分析、变更、实验、踩坑和会话分组，并为每条记录提取一句中文说明。读者可以先看到已有结论和边界，再决定是否进入代码页。完整记录导览避免某个查询只暴露人工挑选的少数笔记。

页面的源码链接直接指向固定工作区中的文件和行。读者需要实现细节时可以进入编辑器，需要影响范围时沿上游、依赖和测试关系继续浏览。内部辅助函数默认收纳在附录，只有任务落到其中时才展开。

Obsidian 提供双链、反向链接、搜索和页面预览，Logseq 提供文件图谱阅读；伴侣插件还可以从选区发起解释，把 CKB 检索证据和回答显示在侧栏，并在同一位置继续追问。每次追问重新检索当前问题，而不是只依赖上一轮文本。

人工反馈也从页面出发。读者针对具体行范围提交意见，系统保存原文和上下文窗口；Agent 处理时先重新定位，再修改来源、生成规则或写入落实记录，最后归档反馈。反馈历史保留，页面仍由生成器控制。

一条完整的人类任务路径可以写成：

```text
任务 → INDEX 选择入口 → 职责导览 → 代码页 → 源码与关系 → 测试入口 → 工作记录
```

这条路径的完成标准不是读者看过多少页面，而是能否形成一个来源明确、影响范围清楚、验证入口可执行的修改计划。

### 第 12 章：Agent 如何在预算内定位代码

Agent 的默认入口是 `brief --profile fast`。它返回一个紧凑 JSON，只暴露问题、预算、Agent pack 路径、完整检索 record、开放反馈数和固定阅读入口。候选实体、词项、得分和关系细节留在 record 中，不在第一轮上下文展开。

典型命令如下：

```powershell
& PYTHON CKB brief --out OUTPUT "QUESTION" --budget 1800 --max-pages 8 --profile fast
```

Agent 先打开预算化 pack。pack 中每个候选都有选择原因、人类知识页、源码路径和范围，以及已经审阅的中文章节。若结果已经足够形成判断，就继续回答或修改；若需要精确符号，再使用 `entity`；需要关系扩展时使用 `neighbors`；需要源码时使用 `source`。

只有检索明确返回 `needs-source-read`，或者 pack 给出了需要核实的精确路径和范围，才进入窄源码读取。`grep` 和全仓遍历保留为补充手段，而不是首轮默认路径。这一顺序把上下文预算花在最可能影响任务的内容上。

复杂跨模块问题可以切换 `precise`。它增加源码 FTS 和固定轮次的加权排序，预算也可以提高。档位变化是显式决策，日常任务不会因为可能存在更远关系而自动扩张为整图分析。

工作记录使用 `changes` 查询，覆盖 analysis、change、experiment、pitfall 和 session；固定实体继续使用 `entity`、`neighbors` 和 `path`。不同命令对应不同问题类型，避免把一切塞进一个通用检索结果。

Agent pack 不是答案，而是来源受控的阅读入口。Agent 仍需判断事实如何影响当前问题，必要时打开测试或源码，并在修改后执行真实验证。检索命中目标文件只是定位任务的完成证据之一，代码行为仍需单独验证。

### 第 13 章：两条路径如何在一次真实修改中汇合

设想一个任务：调整 `fast` 检索的排序，使精确符号命中在预算紧张时仍然保留，同时保持固定关系传播和同分顺序。

人类维护者首先从职责导览进入机器检索区域，了解候选生成、目标保留、关系扩展和 token 渲染是分开的阶段。他看到相关测试入口，并从历史实验中确认 Recall@8、精确符号召回和上下文预算需要分别测量。

Agent 则从 `brief` 开始。问题词命中 `retrieve_machine`、分节索引和导航预算，pack 给出相关页面与源码范围。Agent 再用 `entity` 或 `source` 打开精确实现，而不是在所有 `retrieve` 字样之间自由猜测。

两条路径最终汇合在同一来源：候选窗口在哪里截断，精确目标何时保留，关系权重在哪里加入，预算渲染怎样裁剪。人类页面提供职责与修改理由，机器包提供精确范围和完整候选，两者共同减少错误入口。

修改完成后，验证也分层进行：

1. 单元测试检查目标保留和排序稳定；
2. 冻结查询集比较文件 Recall、符号召回和 token；
3. 重复运行比较结果签名，确认确定性；
4. 真实命令检查 pack 没有超出预算，也没有触发宽搜回退；
5. 变更通过 `record --kind change` 保存原因、文件、测试和边界。

如果需要交付补丁，原始文件先保存哈希，修改在副本验证；最终返回修改产物、补丁、包含命令与退出状态的验证记录，以及有哈希守卫的回滚。回滚在隔离副本执行，确认目标行为和索引回到基线，同时保留无关的并发记录和编辑器状态。

这个例子说明双读者设计的实际价值。人类页面没有替代机器检索，机器检索也没有替代人类判断。它们把同一任务从“相关内容很多”推进到“修改入口、原因、影响和验证都已明确”。

## 第六部分：知识如何持续积累

### 第 14 章：分析、修改、实验和会话记录

固定知识库描述某个 Git snapshot，但项目仍在继续。新的设计判断、代码修改、Benchmark 和失败经验如果只留在聊天或临时日志里，知识库很快会重新与实际工作脱节。

Code Knowledge Builder 将持续知识分成五类：

| 类型 | 记录内容 | 典型用途 |
|---|---|---|
| analysis | 架构判断、方案比较、边界和解释 | 理解为什么这样设计 |
| change | 修改内容、原因、验证、影响和回滚 | 确认已经改变什么 |
| experiment | 冻结协议、指标、结果和失败门 | 比较性能与效果 |
| pitfall | 独立失败原因、环境差异和规避条件 | 避免重复踩坑 |
| session | 一次任务的目标、范围、结果和待继续项 | 恢复任务上下文 |

记录通过统一 `record` 接口进入，而不是直接编辑生成页面。正文使用简体中文，并通过 `--from-pack`、`--from-query` 或现有知识页链接回到固定代码事实。命令生成 Human 页面、Markdown 镜像和机器元数据，再刷新两个 SQLite 索引与 `RECORDS.md`。

稳定代码页和工作记录保持分离。代码页只说明当前有效职责和修改入口；迁移历史、失败尝试、实验数字和回滚证据进入对应记录。这样，读者打开稳定页面时看到的是“现在是什么”，需要历史时再进入工作记录。

生成器从全部笔记统一构建 `RECORDS.md`，每条记录恰好出现一次并带一句中文说明。导览不依赖某次查询关键词，也不会为当前问题手工挑选页面。机器层同时按 Markdown 标题拆节，使 Agent 可以检索某条记录的结论、方法或边界。

构建期间产生的记录可以先排队。人类投影尚未完成时，会话和修改证据进入 workspace metadata；完成后再投影到 Human 层。重新构建或迁移固定图时，这些持续知识按所有权保留，不会跟随生成页面一起消失。

外部参考资料同样拥有独立生命周期。资料可以登记、审阅、更新或标记 superseded，并在机器层形成受控文档；它与源码事实的关系通过分析记录表达。这样既能吸收外部设计方法，也能防止参考材料绕过 Git 来源合同成为“代码事实”。

### 第 15 章：Hook、反馈与跨 Harness 同步

主动调用 `record` 适合经过整理的结论，却容易遗漏会话过程中发生的工具结果和文件变化。自动同步因此按照固定链路设计：触发时机、采集字段、写入形式、后续投影。

**触发时机。** Codex 等 Harness 在 SessionStart、UserPromptSubmit、PostToolUse、Stop 和上下文压缩附近发送事件。不同宿主名称可以不同，但会归一为会话开始、用户轮次、工具结果、文件变化、压缩和结束等固定事件类型。

**采集字段。** 事件保留项目、会话、轮次、工具、退出状态、变化路径和有限摘要。敏感键、授权头、凭据赋值、私钥文本和项目自定义模式在落盘前递归脱敏；字段还有长度上限。未登记项目、缓存、虚拟环境、`node_modules` 和 C# `bin/obj` 由确定性规则过滤。

**写入形式。** 事件先进入原子 spool，再写入 `machine/automation.sqlite`。事件 ID、轮次和路径具备幂等约束，重放和并发不会重复生成记录；失败队列可以显式重试。Git 状态被转换为项目相对路径，避免外层仓库前缀污染当前项目。

**后续投影。** Stop 事件只产生机器层 `pending-agent-review`。Agent 重新打开全部变化路径，写出中文正文、来源核对和精确路径集合后，才会形成一页人类变更记录。原始对话和近原始工具证据保持在机器层，不会随着每次会话扩张稳定页面。

跨 Harness 适配遵循同一核心。Codex 使用 companion plugin 生命周期 Hook，Claude Code 使用项目级 settings，OpenCode 使用对应插件接口，DeepSeek Harness 使用官方事件桥接，通用宿主按照 JSON Schema 至少发送会话开始、用户请求、工具结果和轮次停止。适配层只负责事件来源，去重、脱敏、持久化、分类和审阅留在确定性核心。

人工反馈与自动同步互补。Hook 保存“发生了什么”，反馈保存“人类认为哪一行需要修正”。反馈通过原行范围、全文唯一原文和上下文窗口重新定位；采纳时先修改来源、生成规则或写入落实记录，再归档反馈。反馈历史不删除，开放项继续进入维护门。

自动化的目标不是保存所有文本，而是让关键工作证据不依赖 Agent 自觉，同时仍然经过明确的项目范围、隐私处理和人类审阅边界。

## 第七部分：怎样证明它值得信任

### 第 16 章：机器检索、人类可读性和任务完成

知识库“效果好”可能指很多事情：构建更快、检索更快、上下文更少、目标文件更容易找到、页面更容易读，或者真实修改更容易成功。这些指标彼此相关，也各自拥有独立含义。

机器检索验证需要在运行前冻结问题、目标路径、预算、最大结果、方法顺序、重复次数和阈值。至少分别报告：

- 目标源码 Recall@8；
- 精确符号召回；
- 结果确定性；
- 宽搜回退率；
- 可见上下文 token；
- 冷启动、缓存未命中和稳态 P50/P95；
- 下游任务是否真正形成正确修改与验证计划。

文件 Recall 很高不代表符号定位同样高。一个结果命中目标文件，却没有命中目标类或函数，Agent 仍需读取更大范围。上下文减少也不自动等于成功率提高；它可能只是删掉了噪声，也可能误删必要证据。因此，文件、符号、上下文、延迟和任务结果必须分开报告。

当前 Flask 3.1.3 冻结基线提供了一个经过同轮验证的例子：常驻机器检索中位延迟为 24.9 ms，P95 为 47.6 ms；`git grep` 中位延迟为 73.2 ms，P95 为 86.3 ms；可见上下文从 11,228 tokens 降到 2,294 tokens，减少 79.6%；两者文件 Recall@8 都是 100%，机器检索精确符号召回为 40%，grep 为 100%。这组结果说明上下文和延迟优势真实存在，也同时暴露符号召回仍有改进空间。数字只适用于该冻结仓库、问题集和运行路径。

人类可读性使用另一套任务门：

1. **可发现**：是否命中正确入口，首页到目标需要多少跳；
2. **可理解**：是否能够说清页面职责、进入条件和约束；
3. **可行动**：是否找到源码、影响范围和测试；
4. **可信任**：是否能够追溯来源、审阅和当前状态。

结构审计可以检查标题、标签、中文、双链、源码链接和内部字段泄漏；导航审计可以计算孤立页面和最大跳数；真实任务集则记录目标命中、错误入口、回退次数、完成时间和验证入口。三层结果共同说明人类友好，而不是由页面数量或视觉整洁单独决定。

不同任务还有不同完成证据：定位任务要命中文件并给出符号或进一步查询入口；分析任务要说明方法、原因、效果和边界并进入两个索引；修改任务要给出文件、符号、真实测试、影响和回滚；知识库维护要通过镜像、链接、两个 SQLite、Agent Policy、反馈和 reference 审计。

项目最终追求的是可复查的任务完成，而不是一个漂亮的检索分数。机器路径和人类路径分别验收，最后在真实任务中汇合。

### 第 17 章：当前边界与设计原则

Code Knowledge Builder 的设计建立了稳定边界，也留下了明确限制。

语言理解仍依赖工具条件。缺少 compilation database 的 C/C++、没有正式 project 的 C# 会进入有界近似；语言服务器版本和项目配置可能影响诊断。Parser flag 存在和源码能够解析，只是支持链路的一部分。

确定性检索也有词法边界。FTS、锚点和图传播对可重复性有利，却可能遗漏跨语言同义、隐式职责和极远关系。`precise` 提供更深排序，但仍受输入事实与固定权重约束。向量检索是否加入正式路径，需要冻结 Benchmark 证明净收益，而不是因为语义搜索听起来更先进。

Agent 审阅能够解释代码，却仍可能误读意图。来源范围、测试和相邻关系可以约束推测，也不会把当前实现直接证明为作者的历史意图。正式页面因此偏向描述可由源码观察的职责，设计意图和取舍进入有证据的分析记录。

固定 snapshot 也会随项目演进变旧。overlay 和工作记录可以保存变化，却不会自动让基线实体吸收新 commit。迁移需要重新比较来源、重建变化范围并执行相同审阅与完成门。知识库是一项可维护资产，不是一次生成后永久正确的副产品。

自动同步覆盖多个 Harness，但宿主启动路径、环境变量、事件字段和信任状态仍需分别验证。安装器输出只是中间结果；真实事件是否进入 spool、SQLite 是否写入、Stop 是否形成待审阅记录、人类页面是否在审阅后生成，都需要宿主级 canary。

这些边界没有削弱项目的核心价值，反而说明它的工程原则：

**第一，把确定性放在能够确定的地方。** 集合、排序、预算、配额、状态和门由脚本控制，使结果可以重复、比较和回归。

**第二，把 Agent 放在需要语言理解的地方。** Agent 阅读固定来源、解释职责和权衡，而不是自由决定整个知识库结构。

**第三，让人类和 Agent 共享来源，而不是共享同一种页面。** 机器层保持完整，人类层保持克制，两层分别面向自己的任务。

**第四，让证据先于状态。** 解析、测试、索引、页面、镜像、Benchmark 和回滚都拥有独立入口，完成标记只总结这些证据。

**第五，保留原始事实和长期工作。** 固定源码、机器索引、人类说明、分析、修改、实验、会话和反馈拥有清晰所有权，重建不会抹掉持续知识，持续知识也不会伪装成固定源码。

回到开头的问题：代码已经在那里，为什么还要建立知识库？因为代码保存了事实，却没有天然为每一位新读者组织入口；搜索提供了命中，却没有天然给出修改与验证路径；Agent 提供了语言能力，却需要稳定来源和确定性边界。Code Knowledge Builder 将这些部分连接起来，让一份代码拥有两种合适的读法，并让两种读法最终回到同一个可验证的工程行动。

## 附录 A：从固定源码到双层知识库

一条完整构建链路如下：

```text
干净 Git commit
  ↓ 创建 detached snapshot，保存 commit/blob/range
语言检测与项目选择
  ↓ Tree-sitter 语法事实 + 语言服务器语义证据
分段实体与关系构建
  ↓ facts、provider evidence、diagnostics
确定性页面选择与 Graphify 职责群
  ↓ review packs
Agent 来源绑定中文审阅
  ↓ merge
machine/knowledge.sqlite
  ↓ 确定性 Human 投影
human/ + markdown/
  ↓ 全局审计
.complete + .machine.complete + .human.complete
```

常用构建入口：

```powershell
& PYTHON CKB run --repo REPO --out OUTPUT --format markdown
& PYTHON CKB run --out OUTPUT --resume
& PYTHON CKB finalize --out OUTPUT
```

大型仓库可以拆成 `init`、`build-chunk`、`review-pack`、`merge` 和 `finalize`。任何阶段失败时，先读取状态和对应审计，只返工失败批次或审阅集合。

## 附录 B：从一个问题到修改、验证和回滚

```text
问题
  ↓ brief fast
紧凑 JSON + Agent pack + 完整 record
  ↓ 打开 pack
职责页、源码范围、选择原因
  ↓ entity / neighbors / source（按需）
窄源码读取
  ↓ 修改副本
目标行为测试 + 回归 + Benchmark（按任务）
  ↓ record --kind change
Human/Markdown/两个 SQLite
  ↓ 补丁与验证记录
modified artifact + patch + verification + rollback
  ↓ 隔离回滚探针
恢复目标行为，保留无关并发状态
```

修改任务的最低交付字段包括：修改文件与符号、修改原因、实际命令、输入、字面输出、退出状态、影响范围、补丁和可执行回滚。

## 附录 D：证据如何阅读

本文中的项目结论使用三种证据边界：

- **已确认事实**：能够由固定源码、知识页、命令输出、测试或审计直接支持；
- **分析判断**：由多个已确认事实推导，结论范围与推导依据同时说明；
- **待核验内容**：需要新的仓库、宿主、模型、Benchmark 或真实任务才能确认。

阅读性能数字时，先确认仓库、commit、问题集、预算、重复次数和运行路径；阅读语言能力时，先确认 provider、项目文件和近似标签；阅读自动化状态时，先确认宿主事件、spool、SQLite 和人类审阅是否依次成立。
