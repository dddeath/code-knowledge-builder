## 18:38:17 · 常驻 stdio 检索性能复测（Flask 3.1.3）

来源：[[experiments/常驻 stdio 检索性能复测（Flask 3.1.3）|常驻 stdio 检索性能复测（Flask 3.1.3）]] · 阅览模式选中文本

执行器：Codex / gpt-5.6-sol

### 我的问题

为什么常驻 stdio 能显著降低检索延迟，同时不改变检索结果？

### 选中文本

> 常驻请求中位往返延迟为 23.5 ms，一次性 CLI 为 321.6 ms；结果签名完全一致。

### 解释

**核心含义。** 常驻 stdio 优化的是检索前后的进程生命周期与通信开销，而不是检索算法。一次性 CLI 每次都要重新启动 Python 进程、导入模块并初始化检索资源；常驻进程只支付一次这些固定成本，后续请求直接执行同一个确定性检索核心。因此，23.5 ms 与 321.6 ms 的差距主要来自启动成本被摊销，并非省略了检索步骤。

**在当前上下文中的作用。** 阅读包表明，`scripts/ckb.py` 将 CLI 请求路由到确定性核心，`search_terms` 负责规范化问题，`_terms` 等逻辑执行确定性词项匹配和图扩展。Obsidian 启动时保留 CKB stdio 进程后，相同的查询、`profile=fast`、预算、页数上限和索引数据仍进入这些逻辑，只是绕过了反复拉起 CLI 的外层成本。两种路径的结果签名完全一致，验证了“运行入口的生命周期不同，检索语义相同”。

**容易混淆的边界。** “结果不变”以代码、索引、配置和请求参数相同为前提；索引更新，或查询、档位、预算、页数上限改变时，结果仍可能变化。23.5 ms 是进程已启动后的中位往返延迟，不能当作首次冷启动耗时。常驻也不表示任何缓存都不会影响结果；这里复用的是运行环境，实际检索仍经过同一确定性核心。

**简短例子。** 连续执行同一条 `retrieve --profile fast --budget 1800 --max-pages 8`：一次性 CLI 每次都要启动解释器并初始化资源，常驻 stdio 则从第二次开始直接处理请求。只要索引和参数未变，两者生成的结果签名相同，而常驻请求少了约 300 ms 的固定启动开销。

## 19:20:55 · LLM Wiki 吸收特性与 Flask 检索收益

来源：[[experiments/LLM Wiki 吸收特性与 Flask 检索收益|LLM Wiki 吸收特性与 Flask 检索收益]] · 阅览模式选中文本

执行器：Codex / gpt-5.6-sol

### 我的问题

请解释这段内容中的核心概念、作用、上下文和容易误解的边界。

### 选中文本

> Tree-sitter 与语言服务器构建代码实体和语义证据

### 解释

**核心含义。** 这句话描述的是把源码转成可检索、可追溯知识的两层取证过程。Tree-sitter 根据语言语法生成语法树，从中提取类、函数、方法、字段等代码实体及词法层候选关系；语言服务器再结合项目配置、类型系统和符号索引，判断名称实际指向哪个定义、表达式具有什么类型。前者主要回答“代码写出了什么结构”，后者主要回答“这些符号在项目中具体表示什么”。

**在当前上下文中的作用。** 检索证据将 `scripts/ckb_core/parsers.py` 定位为 Tree-sitter 实体提取、C# `partial` 合并和词法引用关系的实现边。这些结构化结果可作为知识图谱、检索和人类可读 Wiki 的底层材料，使系统能够围绕代码实体及其关系组织证据，而不是只依靠全文关键词猜测。语言服务器若被接入，还可为同名符号、重载和跨文件引用提供更强的消歧依据。

**容易混淆的边界。** Tree-sitter 提取出的语法实体不等于完整语义：它能看见调用的写法，却通常不能仅凭语法树确定重载目标、动态分派结果或外部定义。语言服务器的解析结果也不是运行时事实，并且受构建配置、依赖和索引状态影响。“构建证据”不表示所有关系都已确认，词法候选与已解析的语义关系需要分别标记。尤其要注意，本次阅读包直接证明了当前代码中的 Tree-sitter 提取、`partial` 合并和词法引用职责，但没有直接证明语言服务器语义证据已经接入当前实现，不能把设计目标当成既成功能。

**简短例子。** 两个文件分别声明 `partial class OrderService`，其中一个定义 `Submit(Order order)`。Tree-sitter 可以提取两个类片段和 `Submit` 方法，解析流程再把类片段归并为同一实体；遇到 `service.Submit(order)` 时，语言服务器可结合变量与参数类型确认它指向哪个重载。这里 `OrderService` 和 `Submit` 是代码实体，“该调用解析到这个方法定义”才是语义证据。

## 21:08:18 · Obsidian 多 Harness 选区学习插件

来源：[[changes/Obsidian 多 Harness 选区学习插件|Obsidian 多 Harness 选区学习插件]] · 阅览模式选中文本

执行器：Codex / gpt-5.6-sol

### 我的问题

这个解释功能如何确保 Agent 先使用 CKB stdio 和 Agent pack，而不是把 grep 当成首要检索路径？

### 选中文本

> 解释请求会要求当前 Claudian provider 显式应用 code-knowledge-builder，按开放反馈、retrieve --profile fast、Agent pack、中文解释、record 和审计顺序执行。

### 解释

**核心含义：**这个功能通过“提示约束—CKB stdio 检索—重新读取 Agent pack—生成记录—一致性审计”形成强制证据链，而不是让 Agent 自行选择首要检索工具。插件先通过 CKB stdio 执行确定性的 `retrieve --profile fast --budget 1800 --max-pages 8`，Agent 必须重新打开所得 pack，并以其中的知识页、源码入口和中文摘要为首要证据。只有 pack 明确标记 `needs-source-read`，才允许读取它指定的源码路径；`grep` 最多只能在该分支中辅助定位，不能先于或替代 `retrieve`。

**在当前上下文中的作用：**选区学习插件把这套顺序写入发给 Claudian provider 的解释请求。如果 Harness 没有 Skill 调用器，就改用 `AGENTS.md` 绑定的 CKB CLI 入口执行同一流程。stdio 请求号、pack 路径、分析记录和两份审计文件共同构成可核验凭据；任一步失败，学习页都不应更新。

**容易混淆的边界：**
- pack 已生成不等于 Agent 已使用；仍须重新打开并据此作答。
- pack 列出源码路径不等于授权读取源码。本次 pack 虽列出 `agent_index.py`、`knowledge_layers.py` 和 `machine_knowledge.py` 等入口，但没有 `needs-source-read`，因此不应继续打开源码。
- 审计验证记录来源、中文内容、human/markdown 镜像和 SQLite 索引的一致性，不能把绕过检索、仅凭记忆生成的答案变成合格证据。
- `grep` 不是绝对禁用，但只能在 pack 要求源码核实时进行指定范围内的补充检索。

**简短例子：**本次请求 `obsidian-1788008712015-1` 的 pack 将 `machine_knowledge.py` 概括为实现完整 SQLite 机器知识库及纯确定性 Agent 检索，将 `knowledge_layers.py` 概括为负责人类 vault 镜像与跨层一致性审计，并且没有要求读取源码。因此正确流程是直接依据这些 pack 证据生成解释、追加当日记录并运行审计，而不是先执行 `grep`。

## 21:29:06 · LLM Wiki 吸收特性与 Flask 检索收益

来源：[[experiments/LLM Wiki 吸收特性与 Flask 检索收益|LLM Wiki 吸收特性与 Flask 检索收益]] · 阅览模式选中文本

执行器：Codex / gpt-5.6-sol

### 我的问题

请解释这段内容中的核心概念、作用、上下文和容易误解的边界。

### 选中文本

> 编译式知识库

### 解释

**核心含义**

“编译式知识库”是先通过确定性流水线，把源码或原始材料转换为人类知识页、机器实体与关系、SQLite 索引和按查询裁剪的 Agent pack，再让模型依据这些产物回答问题。这里的“编译”指结构化转换、链接和建索引，不是生成可执行二进制。本次 pack 中的确定性词项匹配、实体全文命中、中文章节命中、图扩展，以及源码定位和知识页回链，体现了这种模式。

**在当前上下文中的作用**

在“LLM Wiki 吸收特性与 Flask 检索收益”的语境中，它把“让模型临时读取全部资料”变成“先离线吸收和组织，查询时只加载预算内的证据”。这样能控制上下文体积，使检索更可复现，并让结论回溯到知识页和源码位置。Flask 即使提供查询接口，也只是运行时入口；编译式知识库才是背后的内容生产、链接和索引层。

**容易误解的边界**

1. “编译式”不等于传统程序编译；产物可以是 Markdown、SQLite 索引和 Agent pack。
2. 它既不等于单独的 Wiki，也不等于单一的向量检索；检索可以组合词项、实体全文、中文章节和图关系等确定性信号。
3. 检索命中只是候选证据，不自动等于正确结论。本次 pack 因 `wiki` 等词项带回了迁移、Obsidian 和自动化测试条目，仍需判断它们是否真正支持问题。
4. 编译产物不会自动永久保持最新；源码改变后需要重新生成、迁移或重建索引。
5. Agent pack 是受预算限制的证据切片，不代表整个知识库；只有 pack 明确标记 `needs-source-read` 时，才应继续阅读其指定的源码范围。

**简短例子**

源码新增 `_note_documents` 后，编译流程抽取该实体及其职责，并更新知识页和机器索引。以后查询 Wiki 文档检索时，系统生成包含源码位置与知识页回链的 Agent pack，模型据此解释；如果源码随后发生变化，旧 pack 便不能继续视为最新事实。
