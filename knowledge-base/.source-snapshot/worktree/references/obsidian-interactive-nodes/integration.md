# Obsidian 原生白板功能节点

## 接入点

- 在既有 Claudian 固定基线 `f4bbba7fd326cbc68a6c8f0edfea6d14ea9ba0ac` 的 `src/main.ts` 加载/卸载入口登记功能节点控制器和右侧 ItemView。保留原有聊天、选区解释与 stdio 路径。
- 插件命令“创建功能节点”“导入功能节点”“打开功能节点面板”只操作当前原生 Canvas。侧栏选择对应白板节点，原生节点选择也同步侧栏；不创建独立 HTML。
- 白板适配器集中检查当前 Canvas 的 `getData`、`setData`、`requestSave` 及视图保存入口。它们不是公开稳定的 Obsidian 类型接口，版本不兼容时只停用功能节点写入，原生白板仍可阅读编辑。
- 模型讨论复用 `ProviderRegistry.createSelectionLearningService`、`resolveSelectionLearningProviderContext`、现有 `InlineEditService.editText/continueConversation/cancel`。该执行器已使用 `passive` 工具策略；不新增模型客户端，不启用 Shell 或任务派发。

## 保存方式

功能节点为 JSON Canvas 的原生 `text` 节点；默认文字只含标题和简短功能说明。节点内命名空间 `ckbFunction` 保存版本、功能单元标识、说明、需求、父单元、输入状态、人工确认以及不透明来源/会话引用。普通节点、其他扩展字段、边、位置和尺寸保留。功能父子关系只画带“包含”标签的普通边，不承载执行。

该命名空间仅属于插件局部数据，不修改知识库固定事实、共同实验导出格式或核心 Schema。原生宿主的节点对象已有 `unknownData` 保存扩展字段；交付前仍必须验证保存、关闭重开和插件卸载后的字段保真，不把内存保存当作磁盘成功。插件卸载后节点保留为可读的普通文本卡。

写入基于当前 Canvas 的实时数据，而非打开侧栏时的旧文件副本；只改对应功能节点及插件创建的父子边。保存操作串行，异常时显示原因，不将损坏数据覆盖为空白。重复导入的单元保留现有内容并报告跳过；悬空/循环父级及损坏引用结构阻止该次写入。

## 人类操作与 Agent 结果

人类可编辑功能说明、需求和父级并明确保存；人工确认单独记录。导入的 `verified` 只展示为输入声明，不等于本插件验收。Agent 回答只进入讨论区，不自动改说明、执行开发或更改验证状态。

来源默认是“来源 1”等短标签，普通入口只说明未绑定；明确展开技术详情后才展示原值。无 Provider 时创建、选择、编辑和保存仍可运行；提问显示可理解的失败状态。取消、换节点、关闭面板及插件卸载释放当前讨论执行器。

## 构建与边界

继续使用 `scripts/build.py` 重放既有补丁，随后重放独立 `interactive-canvas.patch` 并复制功能模块 overlay。新增专项与既有选区解释测试、typecheck、lint、生产构建共同验收。已固定的源码压缩包约 5.3 MB；旧构建目录已清理，本次依赖优先使用本机 npm 离线缓存，不下载 MTNode 或复制完整 CKB 运行时。

仅部署到本任务机器证据目录内的独立测试 vault 和独立 Obsidian 用户数据目录。完整截图、实际命令与返回、可安装插件包、补丁及回滚记录一并交管理验收。

真正的开发派发/执行控制需要管理任务单独确认：当前只接无工具讨论，不添加“执行开发”按钮，也不把关系线接成执行控制。
