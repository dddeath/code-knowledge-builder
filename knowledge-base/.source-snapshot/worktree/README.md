# Code Knowledge Builder

让 Agent 先了解项目，再定位问题、讨论方案和修改代码。

Code Knowledge Builder 为 Git 仓库建立一份有源码依据的知识库：人类阅读中文说明，Agent 查找实现与来源；设计结论和修改记录可以随知识库保留。你不需要学习建库命令，直接把下面的提示词交给 Agent。

## 先选择你要完成的任务

| 你想做什么 | 从哪里开始 | 你会得到什么 |
| --- | --- | --- |
| 先了解本项目 | [了解本项目知识库结构](#了解本项目知识库结构) | 阅读入口、主要功能及源码位置。 |
| 让当前 Agent 使用 CKB | [让 Agent 安装本项目](#让-agent-安装本项目) | 可调用的 Skill，以及明确的安装位置和使用结果。 |
| 让 Agent 理解你的代码仓库 | [让 Agent 解释自己的项目](#让-agent-解释自己的项目) | 项目知识库、中文说明和有来源的回答。 |

已经安装并建库？直接跳到[日常提问与维护](#日常怎么指挥-agent)，或[生成可展开的功能白板](#想用白板看项目结构)。

## 了解本项目知识库结构

你可以先让 Agent 阅读本项目，不必自己下载和寻找文件：

```text
请阅读 https://github.com/dddeath/code-knowledge-builder 已发布的项目知识库，解释这个项目解决什么问题、主要功能如何配合，并给出适合我继续阅读的中文入口。请说明所用知识库对应的源码版本；如果它不是最新版本，明确指出差异，不把旧结论当作当前实现。
```

在带知识库的发布仓库中，内容分为两部分：

- `source/`：项目源码。
- `knowledge-base/`：对应固定源码版本的知识库。

知识库内，人类主要使用以下入口：

| 文件 | 什么时候打开 |
| --- | --- |
| `human/INDEX.md` | 不知道从哪里开始，按任务选择入口。 |
| `human/WIKI.md` | 想了解知识内容如何组织。 |
| `human/RECORDS.md` | 想查找已有方案、实现结论和修改记录。 |
| `human/REFERENCES.md` | 想查看已经收录的外部资料。 |

`facts/` 保留固定源码事实，`machine/` 供 Agent 检索。日常阅读从 `human/` 开始即可。

## 让 Agent 安装本项目

复制以下提示词。项目地址已经填好，不需要自行选择安装命令：

```text
请从 https://github.com/dddeath/code-knowledge-builder 的最新正式 Release 安装 code-knowledge-builder Skill，并按当前操作系统准备运行环境。先检查是否已经安装；已有可用版本时不要重复安装，需要升级时保留恢复方式。请确认当前 Agent 能实际调用 Skill，最后告诉我安装位置、是否可用，以及下一步如何开始使用。本次只安装，不为业务仓库建库；如果当前环境缺少必要能力，请只询问继续所需的信息。
```

**完成后，你应当得到：** 可调用的 Skill、安装位置，以及针对当前 Agent 环境的使用说明。

核心 Skill 和 Obsidian 插件分别安装。不使用 Obsidian，也可以建库和提问；需要白板时，再按下方的[白板提示词](#想用白板看项目结构)安装插件。

## 让 Agent 解释自己的项目

先在 Agent 中打开你的代码仓库，再复制下面的提示词。默认使用当前仓库，不需要重复填写路径：

```text
请使用已安装的 code-knowledge-builder 为当前 Git 仓库建立或接管知识库。已有知识库时先确认它的源码版本，避免重复建库；源码有新提交时，说明并完成必要同步。然后用中文解释项目目标、主要功能和关键流程，给出人类阅读入口与关键源码来源。不要修改业务代码。只有当前工作区没有仓库或存在多个候选时，才询问我选择哪个。
```

**完成后，你应当得到：** 知识库位置、中文阅读首页、项目结构说明，以及可以继续追问的关键功能。

接着直接问具体问题，例如：

```text
请先使用这个项目的知识库，解释一次请求从入口到返回结果的完整流程。只展开理解流程需要的关键实现，并给出来源链接。
```

## 日常怎么指挥 Agent

按目的选择一段提示词即可。默认沿用当前仓库和已绑定知识库，不需要填写工具参数。

### 了解一个功能

```text
请先查当前项目知识库，解释我接下来提到的功能：它完成什么、入口在哪里、主要限制是什么。知识库证据不足时，再读取相关源码，并区分已经确认的实现与待核验的判断。
```

**你会得到：** 功能说明、关键来源和适用边界。

### 修改代码前先定位

```text
请根据我接下来的修改需求，先查知识库中已有的实现与设计记录，找出应修改的位置、受影响的功能和验证方式。先给出方案，不直接修改代码；避免重复实现已有能力。
```

**你会得到：** 可讨论的修改方案、影响范围和建议验证的行为。

### 保留刚刚确认的结论

```text
请把我们刚刚确认的设计结论或实现变化，通过 CKB 写入当前项目知识库。正文说明结论、原因、适用范围和关键来源；尚未确认的内容单独标记。完成后给我阅读链接。
```

**你会得到：** 可再次检索、带来源的知识记录。

### 代码更新后同步知识库

```text
请将当前项目知识库同步到已经提交的源码版本，保留已有笔记、参考资料和研究缺口。先保留恢复基线，在隔离暂存区完成必要更新和验证后再切换。最后告诉我对应版本、主要变化、阅读入口，以及是否还有未完成事项。
```

**你会得到：** 与已提交源码对应的知识库，或明确说明尚未完成同步的原因；未通过验证时保留原库。

## 想用白板看项目结构

Obsidian 是可以打开本地 Markdown 知识库的阅读工具。Canvas 白板是可选的实验功能，不是使用 CKB 的前提。

```text
请从 https://github.com/dddeath/code-knowledge-builder 的正式 Release 选择与当前知识库兼容的 Obsidian 插件，安装到我正在使用的知识库。保留已有设置和白板；如果尚未确定 vault，请只询问应使用哪个。安装后告诉我“生成知识库白板”按钮在哪里，并确认可以查看主要功能及其详情。
```

安装后，点击左侧工具栏或功能节点面板的 **“生成知识库白板”**：

1. 从功能总览按职责逐层展开，或搜索需要了解的功能。
2. 在详情中查看辅助实体和源码入口，而不是面对所有函数平铺的图。
3. 再次生成时保留人类新增卡片、文字、布局和连线。

白板展示当前知识库对应的固定版本；它不会自动修改源码或替你完成知识库同步。讨论功能需要另外配置可用的模型服务，生成和编辑白板不需要模型配置。
